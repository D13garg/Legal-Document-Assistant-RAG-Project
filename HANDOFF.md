### Known limitations (new ones first; also in ADR-040 and the module README)
1. **The answer is returned once and stored nowhere.** A lost response cannot be recovered; a new question is needed (ADR-039 C1, unchanged).
2. **Three transactions in three modules; nothing is atomic across them.** If the link fails after generation, the answer is withheld and an **unlinked generation record and its `generation_recorded` audit fact remain**. No process reconciles or purges these.
3. **No exactly-once generation.** Retries and resubmissions call the provider again and create another record; a completed turn resubmitted appends a second assistant turn. No idempotency key was added.
4. **No single "answer delivered" audit fact**; the trail is three facts per `request_id`.
5. **Candidate documents are caller-supplied.** "Search everything I may read" is unsupported (no `documents` edge or listing API).
6. **`config_id` is operator-declared** and validated for shape only; not a computed fingerprint of the running configuration. Binding it to the evaluated configuration is **Step 17** work.
7. **No HTTP layer exists.** The outer boundary must authenticate and reject disabled principals; `answering` does not. Access Control denies a disabled principal as part of its decision (tested) but that is not a substitute.
8. The proof lifetime is 60 s; a slow search fails closed after the user message is stored.
9. ADR-033 (no streaming of unvalidated text) is satisfied in behaviour but **not authored**; ADR-021 (API versioning) is not applicable until an HTTP surface exists. Both remain `Planned`.

## LATEST CHANGE: Step 9 architecture-guard hardening (detector only; Step 10 NOT started)

Scope: `unverified_provider_calls()` in `tests/architecture/test_ai_gateway_boundaries.py` and its regression tests. No production code, API lock, DAG, ADR, schema or other test file was changed (`generate_text.py` is byte-identical to the baseline ZIP).

**The weakness.** The old detector accepted a `.generate(...)` call if ANY earlier sibling statement (at the call's level or any enclosing level) merely *contained* a `.verify(...)` call anywhere (`ast.walk`). Textual order was treated as proof, so `if condition: verifier.verify(t, e)` followed by an unconditional `provider.generate(r)` was accepted. It was reproduced on the baseline before the fix (returned `[]`, i.e. accepted).

**The fix.** The detector is now a small forward control-flow pass over each scope carrying one fact: "a bare `verify(...)` expression statement has definitely completed on every path to here".
- `if` / `match` / `try` branches are intersected; a branch that raises, returns, breaks or continues is ignored.
- A `try` handler that swallows a failed verify and falls through leaves the code after it unverified (handlers start from the pre-`try` state).
- Only a bare `[await] x.verify(...)` statement is credited. A verify inside `and`/`or`, a conditional expression, an `assert`, a lambda or an argument is not.
- Loops, `with` and `match` are credited only for what runs before them; a verify inside them does not count afterwards (a `with` may swallow the exception). Inside the body it counts normally.
- A nested function, class body or lambda starts unverified (deferred execution).
- Any `x.generate` attribute reference (alias such as `g = p.generate`) and `getattr(x, "generate")` are treated as the provider call.
- Removed the now-unused helpers `parents()` and `has_call()`; `is_call()` and `call_lines()` are unchanged and the previous synthetic assertions are untouched.

**Regression cases added** (`test_verification_must_dominate_every_provider_call`, 1 new test, ~30 assertions). Rejected: conditional verify then unconditional call (the reported defect); `if` with a no-op `else`; verify only inside `for` / `while` / `with` / `match` then a call after; handler that swallows the failure (and a call inside the handler); verify via `and`, conditional expression, `assert`, or as an argument; verify after the call; call in a lambda or nested function after an outer verify; module-level verify with the call in a function; alias and `getattr` access. Accepted (valid patterns preserved): plain verify then call; early-raise guard; verify in both `if`/`else` arms; verify in `else` after a raising `if`; handler that re-raises; the retry loop shape (verify, `try`, call, `continue`); verify and call both inside one `with`; async `await` forms; `finally: pass`.

The frozen DAG (`chunking -> {document_processing, documents, ingestion}`), ADR-010 §4, ADR-037 and this file's Step 7 notes all describe a separate `chunking` module, and the brief's own "consume through a clean public API" and "module-owned receipts" require a module boundary. ### What was built (ADR-038)
