# ADR-005: Object storage strategy

## Status
Accepted

## Context
The shared `ObjectStore` port (Step 1) already fixes tenant-scoped keys (`tenant/<tenant>/<path>`), immutable originals (`put(overwrite=False)` raises on an existing key), an idempotent `delete`, `exists` and presigned GET. Invariant 11 makes document versions immutable. Postgres is the transactional source of truth (ADR-003), and an object store cannot join a database transaction, so every write that spans both needs an explicit ordering and a deterministic recovery path. ADR-032 forbids content caching. Nothing yet fixes the key layout, upload ordering, orphan recovery or limits.

## Problem
Decide where originals live, how an upload is ordered against its database rows, how an object left without a row is found and removed without a manual process, and what limits apply, without new infrastructure.

## Decision
1. **Layout.** One immutable object per document version at `documents/<document_id>/<version_id>/original` (relative to the tenant prefix). Both ids are generated by the use case before any write, so the key is known in advance and never reused. Filenames, titles and media types never appear in a key. Only `documents` writes or deletes these keys.
2. **Limits (configuration slice `documents`, ADR-031).** `max_upload_bytes` (default 50 MiB), `allowed_media_types` (default `application/pdf`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document`, `text/plain`), `upload_intent_grace_seconds` (default 900, minimum 300). A body must be 1 byte up to the maximum and its media type must be in the list. Bytes go through the process: the port offers no presigned PUT.
3. **Upload ordering: intent, object, row.** (a) Transaction 1 records a durable *upload intent* (`documents.upload_intents`: tenant, version id, document id, created at) and enqueues a delayed job `documents:upload_intent` (unique on the version id, `run_at = now + grace`) in the same transaction. (b) The object is written with `overwrite=False`. (c) Transaction 2 requires the intent to still exist (locked), inserts the document/version rows, deletes the intent, audits, and publishes `DocumentVersionAdded`. A row therefore never exists without its object, and an object never exists without an intent or a row.
4. **Deterministic orphan recovery.** If step (c) fails, the use case makes one compensating `delete` attempt and re-raises. Whatever happens, the intent job runs at `run_at` and, only once the grace has elapsed: if a version row exists it deletes the stale intent; otherwise it deletes the object (idempotent), verifies `exists` is false, and deletes the intent. A failed run retries with backoff and finally dead-letters, which is visible. No scanner, no listing of the bucket and no manual cleanup is needed. If the intent is gone when transaction 2 runs (the job already acted), the upload fails with a conflict and its object is removed.
5. **Deletion of originals** happens only through the purge flow of ADR-023.
6. **Reads.** Step 5 exposes no content read path (neither bytes nor presigned URLs); ingestion (Step 6) decides how it obtains originals.
7. **Residual risks (documented, not solved).** A `put` that takes longer than the grace and lands after the intent job finished could leave an orphan; the grace minimum (300 s) must therefore exceed the store client's request timeouts. Bucket versioning, replication and backups can retain deleted bytes (see ADR-023).

## Rationale
A durable intent committed before the first byte is written is the smallest mechanism that lets the system find every possible orphan from its own database, using the existing delayed jobs, with no new infrastructure and no bucket listing.

## Alternatives considered
- Object first, row second with only a best-effort compensating delete: a crash leaves an unfindable orphan.
- Row first (status `uploading`) then object: introduces a visible non-final version and mutable status before ingestion exists.
- Listing the bucket to find orphans: requires a new port method and scans the tenant prefix.
- Presigned PUT: the port has none and it would bypass size and media-type checks.

## Consequences
Two short transactions per upload. A `documents` job queue must be configured. A small table (`upload_intents`) and one delayed job per upload exist until they act. Content never enters Postgres.

## Security implications
Keys carry identifiers only. Size and media-type limits bound abuse. Tenant isolation comes from `TenantScopedKey`. Object bodies are never logged, audited or cached.

## Operational implications
Configure the `documents` queue (`LDA_JOBS__QUEUES`) and the optional `documents` slice. Dead-lettered `documents:upload_intent` jobs mean an orphan needs attention.

## Migration implications
Migration `d0001` creates the `documents` schema including `upload_intents`.

## Amendment (Step 7: content read path)
Superseding §6 and the "no content read path" statement: Documents now exposes `ReadOriginal` (ADR-037), the only way to read an original. It serves only a still-`pending` version of an active document of the caller's tenant, keeps the key layout private, and returns bytes that never reach an event, a log or an audit fact. The key layout, upload ordering and orphan recovery of this ADR are unchanged.
