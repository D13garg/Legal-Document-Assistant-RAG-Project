# ADR-008: Retrieval owns the index projection; ACL scope is live, never projected

## Status
Accepted

## Context
Step 11 implements `retrieval` (roadmap), whose DAG allowlist is `chunking`, `documents`, `access_control`, `ai_gateway` and `ingestion`. ADR-038 §9 left the chunk read path to this step; ADR-014 and ADR-026 define who decides access and what a proof binds; ADR-015 owns version ordering; ADR-023 requires every downstream module to purge its own derived data with a receipt; ADR-017 places prompt/context construction in a later `grounded_generation` module (Step 14); ADR-032 forbids content caches. AG090 reserves construction of authorization-sensitive types to `access_control`.

## Problem
How can retrieval return only what the caller is authorized to see, only from eligible and current versions, with no second copy of permissions, versions or text, and with a purge that cannot lose a race?

## Decision
### Scope and result
1. **Retrieval ends with an authorized, ranked, provenance-carrying result.** `SearchIndex` returns `SearchResult(index_id, hits)`; a `SearchHit` has rank, document id, version id, the version number, chunk id, ordinal, similarity score and the chunk's `text_hash`. No text. It builds no `PromptRequest`/`ContextSegment`, mints no proof, calls no `GenerateText`, and implements no citation or generation record. The result is a plain DTO: it is **not** an authorization proof and **not** an `AuthorizedContext` (none exists in the source tree; retrieval does not invent or construct one). Whoever builds prompt context from hits (Step 14) must obtain a fresh authorization decision and re-read text through `ReadChunks`.

### Authorization
2. **Live scope, no mirrored grants.** The caller passes the `AccessScope` and the proof from ONE Access Control decision for `documents.read_document`. Retrieval keeps no grant table, no permission copy and no cached scope.
3. **Order in `SearchIndex.execute`** (each step before the next is attempted; pinned by tests): (a) the caller must be a principal context and the scope's tenant and principal must equal the caller's; (b) shape validation: non-blank query within the configured length, a limit in `1..max_results`, a non-empty scope of at most `MAX_SCOPE_RESOURCES` (10,000) resources, all of kind `document` with UUID ids, otherwise fail closed; (c) the proof is verified through the shared `ProofVerifier` (production: `EpochCheckedProofVerifier`) against an expectation of exactly the scope's tenant, principal, `documents.read_document` and exactly the scope's resource set, which also enforces expiry and the live policy epoch and principal liveness; (d) only then the query text is embedded; (e) rows are read; (f) the proof is verified once more, so a revocation during the search returns nothing. A scope whose set differs from the proof's fails, so a proof cannot be widened.
4. **Scope bounds the query, never widens it.** The SQL filter is the exact document set plus tenant, index identity and RLS; rows outside the set are also dropped in application code (defence in depth, tested with a repository that ignores the filter). Above 10,000 resources the request fails closed; a large-scope projection is deferred.

### Eligibility and current version
5. **Only `ready` versions are searchable; per document, only the highest-numbered `ready` one.** For every candidate document retrieval asks Documents, per search, about every version it has an index record for and takes the highest-numbered `ready` one. A pending, failed or quarantined newer version never hides an older ready one; a newer ready version hides all older ones; no ready version means no hit; two ready versions with one number is a refusal (inconsistent source). Retrieval stores no status, no number and no "current" pointer; Documents stays the source of truth for ordering (ADR-015).
6. **Additive amendment to `documents.api` (owner-approved, Step 11).** `VersionStateView` and `ReadVersionState` gain `number: int`, Documents' own version number. Nothing else about `ReadVersionState` changes.
7. **Search-time use of `ReadVersionState`, justified.** The use case is declared `@public` with the reason "runs only as pipeline work" and takes a `SystemContext`. Retrieval calls it from the query path, under `SystemContext(tenant, "retrieval:search")`, without changing its contract: it stays a tenant-bound (RLS), read-only lifecycle lookup returning only ids, status and number. It is safe here because authorization is already established by the verified proof before any lifecycle read, the answer is used only to filter results the caller is already authorized for, and nothing from it is returned beyond the version number. The alternative, `GetDocument` per candidate with the caller's context, would repeat the permission check N times and require a permission the proof already covers. The stated reason of the use case is a statement about its original caller, not a restriction the code enforces; if Documents narrows it later, this ADR must be revisited.
8. **Known limit, pinned.** Retrieval can only ask about versions it has an index record for. A version that became `ready` without ever passing the `index` stage is invisible, so an older ready version would remain searchable. The ingestion plan must therefore place `index` before a version can become `ready` (the platform test pins `[extract, chunk, index]` and the fail-closed wrong order). A version ready but indexed only under another embedding identity is handled: it hides the older versions (nothing is served) until rebuilt.
9. **Paging.** Rows are read in pages (`candidate_pool`, default 200) ordered by similarity; each document's decision is made once per search; paging stops when `limit` hits are kept, rows run out, or `max_candidates` (default 2000) rows were inspected. A scope full of superseded rows therefore yields fewer results, never an unbounded scan.

### Reading chunk text
10. **Additive amendment to `chunking.api` (owner-approved; amends ADR-038 §9).** `ReadChunks(ctx: SystemContext, ReadChunksCommand(document_id, version_id)) -> StoredChunks` is the only way another module obtains chunk text and ids. Order of checks: `ReadVersionState` (not found for a tombstoned, unknown, foreign or other-tenant version), status `pending` or `ready` (the `index` stage runs while the version is pending), chunking's own tenant-bound row, then the artifact, whose SHA-256 must equal the recorded hash and which must parse and re-serialise to exactly the stored bytes (so every returned chunk id is one chunking minted). Chunking still mints ids and owns the key layout, which never leaves the module. It takes no lifecycle lock: it writes nothing, and the purge deletes the artifact before the row and the row before the receipt, so a read sees a complete set, finds the row gone, or finds the artifact missing; never partial text. The result is `repr=False` for text and goes to a system caller only. Retrieval's search itself does not call it; the index stage does, and Step 14 will.

### Indexing and purge
11. **`index` stage.** Reads the chunk set through `ReadChunks`, returns early when the version already has a record for this identity (a changed chunk set is `index_conflict`), embeds in batches outside any transaction, then in ONE fenced transaction takes the document's lifecycle lock, refuses if a purge receipt exists (`version_unavailable`) and inserts the record with all vectors atomically. Duplicate delivery changes nothing; a failed commit leaves nothing; a stale executor is rejected by the fence. Permanent codes: `version_unavailable`, `chunks_unavailable`, `chunks_corrupt`, `embedding_invalid`, `index_conflict`; everything else is transient and retried.
12. **`PurgeRetrievalIndex`** is the `ASYNC_JOB` handler of `DocumentPurged` (`retrieval.purge_index`). One transaction: lifecycle lock, receipt check (idempotent), list versions, delete vectors and records, insert-only receipt scoped `retrieval.vector_rows`. A stage after the receipt refuses; a stage before it is seen and removed; no row survives the purge. A duplicate event, a retry after a failed commit and a purge of an unindexed document are all safe.
13. **No `DocumentDeleted` handler (decision, pinned by tests).** From the moment of deletion `ReadVersionState` answers not found, so search returns nothing for the document, and deletion also revokes access. A stage that runs after deletion is refused by `ReadChunks`. The vectors stay unreachable until the purge removes them (ADR-023 retention window). A tombstone copied into retrieval could only lag behind Documents.

### Wiring, logging, failures
14. **Wiring.** `bootstrap/retrieval.py` (`build_index`) takes the chunk reader (`bootstrap/chunking.build_chunk_reader`, an additive builder alongside `build_extraction_reader`), the version-state reader, the proof verifier from Access Control, an embedder and the settings; it registers the purge handler. Configuration slice `retrieval` (`max_results`, `max_query_characters`, `candidate_pool`, `max_candidates`, `embedding_batch_size`); unsafe combinations fail at startup. Bootstrap names avoid domain vocabulary (the Step 1 pin), hence `build_index`.
15. **Content-free by construction.** Retrieval logs, prints and emits nothing (pinned); `SearchQuery` text and proof token are `repr=False`; errors carry only stable codes; driver errors are translated and their cause suppressed. Search and purge are `@public`/`@not_audited` (read-only and derived-data purge; ADR-019 D2), added to the reviewed exemption list; a search audit is deferred with the rest of decision auditing (ADR-019).

## Rationale
The proof already binds tenant, principal, action and the exact resource set and is checked against the live policy epoch; reusing it keeps one decision point. Asking Documents for lifecycle facts on every search keeps ordering and eligibility single-sourced. Doing every write under the document lifecycle lock makes the purge race a matter of lock order, not timing.

## Alternatives considered
Mirroring grants into a retrieval table (a second source of truth that lags revocation); storing a current-version pointer or version number in retrieval or Documents (a projection to keep consistent; rejected by the owner); a `DocumentDeleted` handler (can only lag Documents' tombstone); returning chunk text from search (violates ADR-032/038 and the scope of Step 11); constructing an `AuthorizedContext` (reserved to `access_control`, AG090).

## Consequences
- Retrieval adds `chunking`, `documents`, `access_control`, `ingestion` to its manifest; `ai_gateway` stays unused (ADR-007). Chunking gains a read edge, Documents a field; both locks and the minimal boundary pins changed (listed in HANDOFF).
- A page of results costs one Documents lookup per indexed version of each candidate document per search; it is not cached (ADR-032).
- Not covered here: lexical/hybrid search and reranking (ADR-009), embedding egress (ADR-007 §6), large-scope projection, ANN indexing (ADR-004), rebuild and obsolete-identity cleanup, a search audit.

## Security implications
Authorization precedes everything, is verified twice, binds the exact scope and fails closed on stale, expired, widened or foreign proofs, on oversized or malformed scopes and on any uncertainty. Tenant isolation is the predicate plus forced RLS. The result is explicitly not an authorization artifact. No content in logs, errors, metrics, traces or audit. Static pins are tripwires; behaviour is carried by the tests.

## Operational implications
Per search: one proof verification before and after, one Documents lookup per indexed version of each candidate document, bounded paging (`candidate_pool`, `max_candidates`). The `events` queue must be configured for the purge handler; the pipeline plan must include `index` before a version can become `ready`. Dead-lettered purge jobs need the usual operator attention.

## Migration implications
Additive API changes: `chunking.api.ReadChunks` and `documents.api.VersionStateView.number` (locks regenerated); additive `bootstrap.chunking.build_chunk_reader`; minimal allowlist updates to the pins that name importers and exemptions (listed in HANDOFF). No data migration of earlier steps.
