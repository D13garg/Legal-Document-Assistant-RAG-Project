# ADR-010: Async ingestion and PipelineStage inversion

## Status
Accepted

## Context
Invariant 10 (stages idempotent under at-least-once delivery) and invariant 11 (only `READY` versions are searchable) need a pipeline that moves a document version from `pending` to a terminal state. The module DAG fixes the direction `documents -> ingestion`, `document_processing -> ingestion`, `chunking -> ingestion`, `retrieval -> ingestion`, and `ingestion -> {}`: ingestion imports no module, so it cannot know Documents' ids, events, tables or statuses (ADR-027 forbids cross-schema access as well). ADR-012 gives a transactional Postgres queue; ADR-028 gives event delivery; ADR-015 left the `pending -> ready/failed` machinery to Step 6; ADR-005 §6 left "how ingestion obtains originals" open.

## Problem
Define who owns what, how a version enters and leaves the pipeline, how stages plug in without an import cycle, what `READY` means, how failure, retry, dead-lettering, replay, cancellation and recovery behave, and what Step 6 deliberately does not do.

## Decision
1. **Ownership.** *Documents* owns the document/version lifecycle and is the only writer of `documents.versions.status`. *Ingestion* owns ingestion runs, stage runs, job handling and ingestion outcomes (schema `ingestion`). The two meet only through jobs, events and the public APIs the DAG permits (`documents -> ingestion`).
2. **Start.** Documents registers an `ASYNC_JOB` handler for its own `DocumentVersionAdded` that enqueues one ingestion job through the shared `JobQueue` of the handler's transaction, using `ingestion.api.ingestion_job_spec(document_id, version_id)` (queue `ingestion`, type `ingestion:run`, unique key `ingestion:run:<version>:<generation>`, generation 1). Ingestion's payload carries two opaque ids and a generation; **never a tenant** (the tenant comes from the job row, ADR-012/013). Step 5's upload use cases are untouched.
3. **Run and stages.** A run is identified deterministically (`uuid5` over tenant, version, generation) and is created by the first execution (or by replay). Its stage list is the configured plan frozen at creation. Run status: `running`, `completed`, `failed`, `quarantined`, `dead_lettered`, `cancelled`. Stage status: `pending`, `running`, `succeeded`, `failed`, `quarantined`. Transitions are validated by the domain **and** by database triggers. `completed`, `failed`, `quarantined`, `cancelled` are terminal; `dead_lettered` can only be cancelled (or superseded by a replay, which creates a new generation).
4. **PipelineStage inversion.** `ingestion.api` defines `PipelineStage` (`name`, `run(StageRequest) -> StageOutcome`), `ContentScanner` and the outcome types. Later modules (`document_processing`, `chunking`, `retrieval`) implement `PipelineStage` and import `ingestion.api` (edges already in the DAG). `bootstrap` composes the ordered plan. Stage outcomes are exactly `StageSucceeded`, `StageRetryable(error_code)`, `StagePermanentFailure(error_code)`, `StageQuarantined(error_code)`. An exception raised by a stage is a retryable failure carrying the exception's `LdaError.code` (or `stage_exception`). Error codes are free-form identifiers (`[a-z][a-z0-9_.]{0,63}`); **no fixed failure taxonomy is imposed in Step 6**.
5. **The plan.** The first stage is always the mandatory `scan` stage (ADR-036); the configured stages follow. **Production composition rejects an empty list of configured stages** (`ingestion_pipeline_empty`), names must be unique, valid identifiers and not `scan`. Step 6 ships fake stages only in `ingestion.testing`; no real stage exists, so no real document can reach `READY` through Step 6 alone.
6. **What `READY` means in Step 6.** A run is `completed` only when the scan verdict was clean **and** every stage of its frozen plan succeeded in order. Completion is a domain invariant of the run (`IngestionRun.complete` refuses otherwise) and is the only source of `IngestionCompleted`. It is not "the job finished". Documents moves a version to `ready` only on that event. Later steps extend the plan; they never weaken this condition.
7. **Outcome events.** In the same transaction as the terminal run transition, ingestion publishes `IngestionCompleted(document, version, run, stage_count)`, `IngestionFailed(..., error_code)` or `IngestionQuarantined(..., error_code)` (`ASYNC_JOB`, identifiers only). Documents handlers call its own `RecordVersionOutcome`, which applies `pending -> ready | failed | quarantined` with a compare-and-set on the version row, audits it, and never touches a version that is not `pending`, a tombstoned document, or an id pair that does not match. Documents then calls ingestion's `AcknowledgeOutcome`.
8. **Failure semantics.** `StagePermanentFailure` -> run `failed` -> version `failed`. Scan `infected` -> run/version `quarantined`. `StageRetryable` -> the stage returns to `pending`; the handler asks the worker to retry (it raises a coded error; the platform applies its existing jittered backoff) until the job's `max_attempts` is reached, at which point the run becomes `dead_lettered` and the job is failed (dead). **A dead-lettered run leaves the version `pending`** (not searchable, not failed). The retry budget is the queue's `max_attempts` (the `JobSpec` default); it is shared by all stages of a run. No new retry numbers are introduced.
9. **Replay.** `ReplayIngestion` is an audited, tenant-bound use case. It is allowed only when the latest generation of a version is `dead_lettered`; it creates the next generation (run row + job with the next unique key + watchdog) in one transaction. It never touches `failed` or `quarantined` runs and never resets a version. Which principal may replay is **a later API-layer responsibility** (`@requires("ingestion.replay_ingestion")` is declared, not enforced; ADR-014/Step 16).
10. **Cancellation and cleanup.** Documents registers handlers that call ingestion's `CancelIngestion` on `DocumentDeleted` and `PurgeIngestionRecords` on `DocumentPurged`. Ingestion owns and deletes **only ingestion-owned state** (runs, stage runs) and writes **no purge receipt**: Documents and later modules keep their own receipts (ADR-023). Known limitation: a job that is claimed after a purge can recreate a run for an unknown version; Documents' outcome handler then finds no version and calls `PurgeIngestionRecords` again, so state converges.
11. **Recovery (watchdog).** Creating a run enqueues one delayed `ingestion:watchdog` job per run (unique key). When it fires: a `running` run with no progress for `watchdog_delay_seconds` is dead-lettered (`watchdog_stalled`, closing the gap where the job died without reaching a handler; never a hidden replay); a terminal run whose outcome is unacknowledged is re-published with a new event id, at most `max_outcome_redeliveries` times; everything else is done or reschedules itself without consuming attempts. Recovery is tenant-bound, idempotent and fail-closed. There is no global tenant sweep and no tenant registry. `watchdog_delay_seconds` must exceed `lease_seconds + backoff_cap_seconds` and the longest single stage attempt; bootstrap checks the first bound.
12. **Idempotency and fencing.** Every ingestion write transaction (a) verifies the job's fencing token through `uow.fence.verify` (ADR-012 amendment) and (b) locks the run row and applies a state compare-and-set. Deterministic run ids and unique keys make duplicate delivery a no-op. Stage implementations must be idempotent and must fence their own effect transactions with the same `fence.verify`; `StageRequest` carries `job_id` and `fencing_token` for that purpose.
13. **Bytes.** Step 6 moves no bytes: the fake stages and the fake scanner see identifiers only. How a real scanner or stage obtains originals (the key layout is Documents'; ADR-005 §6) is **not decided here**; it must be decided with the first real stage (Step 7) and must not make ingestion import Documents.
14. **Observability.** Per stage run: attempts, duration, status, error code. `GetIngestionMetrics` aggregates them per tenant (runs by status, dead-lettered runs, unacknowledged outcomes, per-stage retries/failures/average and maximum duration). Queue depth, oldest age and dead jobs come from `JobMaintenance.metrics`. Logs carry allow-listed identifiers only (`stage`, `outcome`, `error_code`, `duration_ms`); no exporter (ADR-020).
15. **Audit.** Documents audits terminal version transitions (`documents.version_outcome_recorded`); ingestion audits replay (`ingestion.ingestion_replayed`). No per-stage audit.

## Rationale
Inverting the dependency lets the later modules plug in without ingestion importing them, while keeping the version status under its owner. Doing every state change and its event in one transaction on the existing queue removes any outbox. The watchdog is the Step 5 delayed-job pattern applied to runs.

## Alternatives considered
- Ingestion writes the version status directly: violates ADR-027 and the DAG.
- Upload use cases enqueue the ingestion job: edits frozen Step 5 code for no benefit; the event was designed for this.
- Re-enqueue a recovery job from the watchdog: hides a replay and needs a recovery budget.
- A global sweep for stuck versions: needs a tenant registry that does not exist.
- A fixed failure taxonomy or retry budgets per stage: not specified, would be invented.

## Consequences
Two small transactions per stage; stage effects of future modules must be idempotent and fenced. A queue backlog longer than the watchdog delay can produce a false `dead_lettered` run, which fails closed (the job later finds the run inactive and does nothing) and is recovered by an explicit replay. The version stays `pending` until an outcome arrives.

## Security implications
Tenant comes only from the job row; a forged payload id can at worst create an inert run in the job's own tenant, because Documents verifies the version under RLS before acting. Events carry identifiers only. Quarantined versions can never become `ready` (trigger). Uploaded content is untrusted and never read by ingestion in Step 6.

## Operational implications
Configure the `ingestion` and `events` queues in `LDA_JOBS__QUEUES` and register `container.job_handlers`. Dead `ingestion:run` jobs and `dead_lettered` runs need alerting (Step 18). The `ingestion` slice has `watchdog_delay_seconds` and `max_outcome_redeliveries` (operator settings, not retry budgets).

## Migration implications
Migration `g0001` creates schema `ingestion`; Documents migration `d0002` widens the version status machinery (ADR-015 amendment); platform migration `p0002` adds the fencing token (ADR-012 amendment). All additive.

## Amendment (Step 7: bytes)
Superseding §13: how a stage obtains the original is decided by ADR-037 (`documents.api.ReadOriginal`, called by the stage; ingestion still imports no module and still moves no bytes). `StageRequest`, `PipelineStage` and the outcome types are unchanged. The first real stage is `extract` (module `document_processing`); the mandatory `scan` stage still has no real scanner, so end-to-end `ready` still requires one at composition.

## Amendment (Step 18, 2026-10-18)
"Alerting (Step 18)" is met only partially: `JobMaintenance.dead_letter_summary` and `overdue_lease_count` give read-only visibility by job type; no alerting, exporter or dashboard exists. The convergence described in §10 (a run job claimed after purge) is now pinned by a real-PostgreSQL test. See ADR-042.
