# ADR-014: Authorization model, resource registry, AccessScope and policy epoch

## Status
Accepted

## Context
Invariant 3 (`architecture.md` §4) requires default deny, live ACL evaluation and a `policy_epoch` that moves with every relevant change. Invariant 1 requires authorization to precede content. Until step 3 the repository had these as principles only: it fixed the place of `access_control` (depends on `identity`; `documents`, `retrieval`, `citations`, `grounded_generation`, `answering` depend on it), the names `AccessScope` and `AuthorizationProof`, and ADR-034's opaque `@requires` labels, but no policy model, no resource vocabulary and no epoch semantics. The previous step-3 session stopped rather than invent them. The owner has since approved decisions D1-D8; this ADR records the authorization half (the proof and egress half is ADR-026). ADR-022 (security model and untrusted-content handling) is **deferred**: only the semantics Access Control and the LLM egress boundary need are decided here and in ADR-026.

## Problem
Fix the smallest authorization model that is default-deny, tenant-isolated, revocable with a fail-closed guarantee, and implementable without reading any other module's tables or moving authorization semantics into the kernel.

## Decision
1. **Policy model (D1).** Authorization is a set of explicit, per-principal grants of `(resource, action)`. The decision is default deny: no grant, no access. There are **no roles, groups, inheritance, wildcards, deny rules, conditions or time-limited grants in v1**. Older material that mentions roles does not change this; adding any of them needs a new ADR.
2. **Resources (D2).** A resource is `ResourceRef(kind, id)`. `kind` is a lowercase identifier (`[a-z][a-z0-9_]*`, at most 64 characters); `id` is an opaque string owned by the owning module (`[A-Za-z0-9][A-Za-z0-9._:-]*`, at most 128 characters). Access Control never interprets an id and never reads the owning module's data.
3. **Registry (D2).** Access Control owns the resource registry: for each resource kind, the set of actions allowed on it. Owning modules register their kinds and actions **through the Access Control API** (`ResourceRegistry.register(ResourceKindDefinition(...))`) from their bootstrap wiring. The registry is **code-defined, in-process and sealed at composition**: registering after sealing, registering a kind twice, or a definition with no actions is an error. It is not a database table. A grant can only be created for a registered `(kind, action)`, and the authorization decision only ever honours registered pairs: an unregistered kind or action is denied even if a stale grant row exists.
4. **Actions and `@requires` (D3).** An action is a dotted identifier with the ADR-034 shape (`documents.read_document`, `identity.read_principal`). A use case's `@requires("...")` string is an action in this vocabulary; the kernel still treats it as an opaque label (ADR-034 is unchanged and `shared/kernel` gains nothing). Only Access Control interprets it.
5. **Grants live in the Access Control schema (D2).** Schema `access_control` (equals the module name, ADR-027): `access_control.grants` keyed `(tenant_id, principal_id, resource_kind, resource_id, action)` and `access_control.policy_epochs` keyed `tenant_id`. Both have forced RLS on `tenant_id`. There are **no foreign keys** to any other schema, including `identity.principals`; principal existence is verified through the Identity API at grant time, not by constraint. Revocation deletes the row; the runtime role may `SELECT, INSERT, DELETE` grants and `SELECT, INSERT, UPDATE` epochs.
6. **Use cases.** `GrantAccess` and `RevokeAccess` (`@requires("access_control.grant_access")` / `("access_control.revoke_access")`, `@audited`), and two decision queries (`@public`, `@not_audited` with a reason that defers decision auditing to ADR-019): `AuthorizeAction` (strict: allow only if **every** requested resource is granted for the action) and `ResolveAccessScope` (filter: the scope is exactly the granted subset of the candidates; empty means deny). Both take the principal from the `TenantContext`; a `SystemContext` is refused (`authorization_requires_principal`), so platform code cannot ask for a decision on behalf of an arbitrary principal. Tenant is always `ctx.tenant_id`; requests carry no tenant.
7. **`AccessScope` (D4).** A frozen value: `tenant_id`, `principal_id`, `policy_epoch`, `resources` (a `frozenset[ResourceRef]`). `resources` is the **exact** authorized set used to build or filter the authorized retrieval context. It is not a permission cache and has no operation that widens it or re-resolves it. `AccessScope` is added to the archguard restricted constructors (AG090, `policy.py`): only `access_control` code (including its `testing/` builders) may create one. A scope holds at most 10,000 resources (v1 guard; ADR-008 revisits it with retrieval).
8. **`policy_epoch` (D5).** One monotonic integer per tenant. A tenant with no row has epoch 0. Every grant or revocation that **changes** the grant set advances the epoch by exactly 1 **in the same transaction** as the change; an idempotent grant of an existing row or revoke of an absent row changes nothing and does not advance it. A database trigger rejects any epoch update that is not `+1` (the epoch can neither move backwards nor skip). Decisions read the epoch **before** the grants, in one transaction, so a concurrent change can only make a decision look older than the grants it saw (the proof is later rejected, fail-closed), never newer.
9. **Identity boundary (D5).** Every decision calls `identity.api.GetPrincipal` live. A principal that is absent, belongs to another tenant, or is `disabled` is denied (`principal_not_active`). Principal status is never cached or copied into Access Control. `GetPrincipal` stays `@public` (ADR-035 asked for this to be revisited: authorization must be able to ask who a principal is, so requiring authorization to ask would be circular). No event-driven or eventually-consistent path exists for this decision.
10. **Decision shape.** `AuthorizationDecision` is `ALLOW` (with `action`, `scope` and an `AuthorizationProof`, ADR-026) or `DENY` (with a `DenyReason`: `principal_not_active`, `not_granted`, `unknown_action`, and no scope or proof). A denial never reveals which of several requested resources lacked a grant beyond the reason code.
11. **Enforcement (D8).** Access Control exposes use cases only. There is no HTTP middleware and none is invented here; `@requires` wiring at the API layer is a later step. Until then `@requires` remains declaration-only everywhere except where a caller invokes the decision use cases itself.
12. **Dependencies and configuration.** `access_control.depends_on = ["identity"]` (the approved edge). The first module configuration slice (`access_control`, ADR-031) holds the proof signing key (ADR-026). Because module slices may not import `platform`, the configuration loader's type bound is relaxed from `SettingsSlice` to pydantic `BaseModel` (an ADR-031 amendment; behaviour is unchanged).
13. **Explicitly out of scope.** Roles/groups, delegation, ownership inheritance, tenant membership, authentication, an administrative bootstrap for the very first grant, decision auditing (ADR-019), the HTTP layer, retrieval filtering, and the security model for untrusted content (ADR-022, deferred).

## Rationale
Explicit grants are the smallest model whose result is a finite resource set, which is exactly what `AccessScope`, the proof and the retrieval projection need. A code-defined registry avoids a global (non-tenant) table, a cross-tenant system scope in RLS, and per-deployment catalog drift. A single per-tenant epoch advanced in the grant's own transaction makes revocation a plain consequence of commit order and needs no events or timers. Reading the epoch first makes the only possible race fail closed.

## Alternatives considered
- RBAC (roles, groups): rejected by D1; adds a second resolution layer between a principal and the exact resource set.
- A persisted registry table: global data in a tenant-RLS design needs a sanctioned cross-tenant path (ADR-013) and a migration per owning module.
- Per-principal or per-resource epochs: more precise, but proof verification would need to know which to read; one tenant epoch is simpler and fails closed.
- Caching principal status or grants: rejected (D5); a cache is a revocation delay.
- Foreign key from grants to `identity.principals`: forbidden by ADR-027.
- A single combined decision use case with an "all or nothing" flag: a boolean that flips security semantics is easy to misuse; two named use cases are explicit.

## Consequences
- Revocation is fail-closed once the revoking transaction commits (together with ADR-026's live epoch check), but a decision already returned to a caller is not recalled.
- Granting is not self-bootstrapping: `@requires("access_control.grant_access")` cannot be satisfied by an empty policy. The administrative bootstrap of the first grant is open and needs its own decision when the API layer exists.
- Scopes larger than 10,000 resources are refused until retrieval defines its projection.
- Hard-deleting grants leaves no history; the audit module (ADR-019) is expected to record grant and revoke facts.

## Security implications
Default deny; tenant by construction (tenant from the execution context, tenant-bound repositories, forced RLS, tenant-leading primary key); no cross-module reads; unregistered kinds/actions are unreachable; `AccessScope` cannot be fabricated outside the module (AG090). `GetPrincipal` is queried live so a disabled principal is denied immediately at decision time. Disabling a principal does **not** advance `policy_epoch` (Identity has no knowledge of Access Control); instead proof verification re-checks the principal's status live through the same Identity boundary (ADR-026 §7), so a disabled principal's outstanding proofs stop verifying immediately.

## Operational implications
Deployments run the `access_control` Alembic branch (`extra_locations`) and need the `access_control` configuration slice (ADR-026). Every owning module's bootstrap must register its resource kinds before the registry is sealed; sealing happens in `bootstrap/access_control.py`.

## Migration implications
Introduces the `access_control` branch (`a0001`): schema, `grants`, `policy_epochs`, the epoch-step trigger; downgrade drops the schema. Adding a resource kind or action is a code change in the owning module; removing one makes existing grants inert, not invalid.

## Amendment (Step 5, ADR-023)
Access Control gains one additive capability: removing **every** grant on one resource and advancing the tenant's policy epoch exactly once when at least one grant was removed, inside the caller's transaction. It is exposed as `GrantRepository.remove_all_for_resource` and as the adapter `SqlResourceAccessRevoker` for the shared port `ResourceAccessRevoker` (`lda.shared.ports.access_revoker`), constructed by bootstrap and handed to the owning module's unit of work, like `AuditRecorder`. It is not a use case and not an HTTP surface; decision logic, the registry, the epoch step trigger and `D1-D8` are unchanged, and there is no new module edge.
