# ADR-026: Authorization proof and the LLM egress chokepoint

## Status
Accepted

## Context
Invariant 1: text reaches a provider only inside an authorized context whose proof is verified at egress. ADR-014 defines who may see which resources; this ADR defines the artifact that carries that result to the provider boundary and how the boundary checks it. The approved decisions are D6 (proof is HMAC-bound, carries a key id, only Access Control signs, `ai_gateway` must not depend on `access_control`, the verification contract lives in `shared/ports`) and D7 (60-second lifetime; verification checks integrity **and** the live tenant `policy_epoch`). `ai_gateway` is step 9 and does not exist yet, so this step defines and tests the contract and the composition point, not the gateway. ADR-022 (security model and untrusted-content handling) is deferred; only the egress semantics are decided here.

## Problem
Make "this exact set of resources was authorized for this principal and action, just now" something the provider boundary can verify without importing Access Control, without trusting the caller, and with revocation that fails closed.

## Decision
1. **What a proof binds (D6).** Tenant, principal, action, the **exact authorized resource set**, `policy_epoch`, issued-at and expiry. The resource set is bound by a SHA-256 digest of its canonical form (refs sorted by `(kind, id)`; each length-prefixed; domain-separated by a version tag) plus the resource count, so a scope of thousands of documents does not inflate the token. The verifier recomputes the digest from the set the caller presents; any added, removed or substituted resource changes it.
2. **Token format.** An opaque string `v1.<key_id>.<payload>.<mac>`. `payload` is canonical JSON (sorted keys, compact separators, UTC integer seconds) in unpadded base64url; `mac` is HMAC-SHA256 over a domain tag, the key id and the payload segment, so the key id is itself authenticated. The payload is parsed only after the MAC verifies (constant-time comparison); tokens longer than 2048 characters, with other than four segments, non-canonical base64, extra or missing claims or wrong claim types are rejected as malformed.
3. **Lifetime (D7).** Exactly 60 seconds, a domain constant (not configuration, so it cannot be widened by a deployment). A verifier also rejects any token whose `exp - iat` exceeds 60 seconds.
4. **Minting.** Only `access_control` can mint. The signing key exists only in its configuration slice and keyring; `AuthorizationProof` is already restricted to the module by AG090; a proof is created only inside the two decision use cases, in the same unit of work and from the epoch and grants that produced the `AccessScope` (ADR-014 §8). There is no separate "issue a proof" operation and a proof is never minted for a denial or an empty scope.
5. **Verification contract (D6).** `lda.shared.ports.authorization` defines `ProofVerifier` (one method, `verify(token, expected)`), `ProofExpectation` (tenant, principal, action, resources) and `ProofResource` (the neutral `(kind, id)` wire form of a resource). The port imports only the kernel. `ai_gateway` will depend on this port, never on `access_control`; `module-dag.toml` is unchanged (`ai_gateway.depends_on = []`).
6. **Concrete verifier and injection.** `EpochCheckedProofVerifier` lives in `access_control.application` and is exposed through its `api`. It is built with the keyring, the Access Control unit of work, the Clock **and `identity.api.GetPrincipal`** (the existing, approved Identity boundary; no new dependency edge). `bootstrap/access_control.py` builds it and hands it out typed as the shared `ProofVerifier`; the composition root injects it into `ai_gateway` at step 9. No module other than `bootstrap` needs to import it.
7. **Verification rule (D7, final form per the owner's Step 3 close-out decision).** A proof is valid **only when all five hold**: (1) HMAC integrity and canonical encoding (token shape, known key id, constant-time MAC, strict base64url); (2) the binding: every claim equals the expectation (tenant, principal, action, resource digest and count); (3) `now < exp` and lifetime ≤ 60 s; (4) the claim's `policy_epoch` **equals** the tenant's live epoch, read in a fresh transaction scoped to `expected.tenant_id`; (5) the referenced principal is **currently active**, read live through `identity.api.GetPrincipal` in the expected tenant. The checks run in that order and the first failure is reported; cheap in-memory checks (1-3) run before any database read, and the principal check runs last. A correctly signed proof with a stale epoch is rejected (revocation does not wait for expiry), and a correctly signed, unexpired, current-epoch proof is rejected the moment its principal is disabled. Principal status is never cached or copied; Identity does not bump `policy_epoch` and gains no dependency on Access Control. Validity is a conjunction evaluated afresh on every call: nothing latches a denial, so re-enabling a principal does not by itself make an expired, stale or otherwise invalid proof valid, while a proof that still satisfies all five rules verifies again.
8. **Failure behavior.** Verification either returns or raises; there is no "soft" result. Rejections raise `AuthorizationError` with stable codes `proof_malformed`, `proof_unknown_key`, `proof_signature_invalid`, `proof_mismatch`, `proof_expired`, `proof_stale_epoch`, `proof_principal_inactive` (principal disabled, absent, or in another tenant: Identity makes those look the same). A database failure while reading the epoch or the principal raises `InfrastructureError` and also means **no egress** (fail closed; no retry-with-fallback, no cached epoch or status). Codes are for internal diagnostics; a client sees one generic denial. Tokens, claims and key material are never placed in errors, logs or audit (`ProofClaims`, `AuthorizationProof` and `SigningKey` redact `repr`).
9. **Egress chokepoint (contract for step 9).** Every `ai_gateway` operation that sends text to an external provider must call `ProofVerifier.verify` with an expectation built from the content it is about to send (tenant and principal from the execution context, the action, the resource set that produced the segments) **before** the provider call, and must not call the provider if verification does not return. Step 9 owns the architecture test for this; until `ai_gateway` exists the rule is a contract, not an enforced property.
10. **Keys (D6).** Configuration slice `access_control` (ADR-031): `proof_key_id` (`[a-z0-9][a-z0-9_-]{0,31}`) and `proof_key` (`SecretStr`, base64url, at least 32 decoded bytes). One active key in v1. The token carries the key id and the verifier resolves keys through a keyring, so verify-only keys for rotation can be added later without changing the token format; rotation itself is not implemented.

## Rationale
Binding by digest keeps the proof small yet exact. Checking the live epoch at the provider boundary turns the 60-second lifetime into a bound on replay, not on revocation. Putting only the contract in `shared/ports` keeps the DAG unchanged and keeps provider code from linking to the policy module. Making verification raise rather than return a flag removes the "forgot to check the boolean" failure.

## Alternatives considered
- `ai_gateway -> access_control` edge: rejected by D6; it would also make the provider boundary depend on policy internals.
- Embedding the full resource list in the token: large and gains nothing over a digest when the verifier is handed the set.
- Expiry-only revocation: up to 60 s of stale authorization; rejected (D7).
- Asymmetric signatures: no third party needs to verify; verification already requires a database read inside the same deployment.
- A boolean-returning verifier: easy to ignore.

## Consequences
- Every provider call costs one epoch read and one principal read. Egress is unavailable while the database is unavailable (intended).
- Any grant or revocation for a tenant invalidates that tenant's outstanding proofs; callers must re-authorize. Long retrieval/generation pipelines must finish within 60 seconds of authorization or re-authorize.
- **Principal disablement (closed by the owner's Step 3 close-out decision):** disabling a principal still does not advance `policy_epoch`, but the verifier checks status live, so every outstanding proof of that principal is rejected on the next verification (`proof_principal_inactive`), with no waiting for expiry. Decisions already returned to a caller are not recalled, and text already sent is not unsent; the guarantee is for egress that has not yet happened.
- HMAC key compromise allows forging proofs until the key is replaced; key storage and rotation operations are deployment concerns.
- The shape of `ProofResource` duplicates `ResourceRef` on purpose: the port must not import Access Control types.

## Security implications
Unauthorized content cannot be sent unless an attacker can forge an HMAC, replay a still-valid proof for the identical tenant, principal, action and resource set within 60 seconds with no intervening grant change, or `ai_gateway` fails to call the verifier (the step-9 contract). A disabled principal cannot egress at all. Tamper, wrong tenant, wrong principal, wrong action, wrong resource set, expiry, stale epoch and a disabled principal are each tested. Secrets are `SecretStr`, never echoed by configuration errors, and compared in constant time.

## Operational implications
Deployments must set `LDA_ACCESS_CONTROL__PROOF_KEY_ID` and `LDA_ACCESS_CONTROL__PROOF_KEY`; bootstrap fails fast if they are missing or weak. All instances must share the key and a reasonably synchronized clock (expiry is checked with the verifier's clock).

## Migration implications
Token version `v1` is part of the format; a future change bumps the version and the verifier rejects unknown versions. The port is ADR-governed (`shared/ports/*`): changing it needs an ADR amendment.

## Amendment (Step 3 close-out): live principal-status check
The owner closed the one open Step 3 decision: verification must also check the principal's live status (rule 5 in Decision §7). Implemented by giving `EpochCheckedProofVerifier` the existing `identity.api.GetPrincipal`; Access Control's `depends_on = ["identity"]` is unchanged, Identity is untouched and does not know Access Control, and `policy_epoch` is still advanced only by grant changes (ADR-014 §8). D1-D8 are otherwise unchanged. The constructor of `EpochCheckedProofVerifier` is part of the module's public API, hence the `api.lock` update under AG080.
