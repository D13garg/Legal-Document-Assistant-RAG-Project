# ADR-029: Grounded generation

## Status
Accepted

## Context
Approval state (2026-10-16): D1-D7 were **owner-approved** on 2026-10-15 and **D8 was owner-approved** on 2026-10-16 (Owner decision record below). Every approval is a **project-owner approval only**, a conversation record and not a repository sign-off: no approval by `@legal-rag/ai-quality`, security, legal, architecture or any other person or team is claimed. The D4 outage semantics, superseded-version eligibility and the CODEOWNERS route (left unrouted) were owner-decided on 2026-10-15. Status is `Accepted`, together with the decisions-log row, because every gate recorded in this ADR is satisfied; it is a project-owner acceptance, and organizational ownership policy may still require a later review. The limitations stated below are unchanged by acceptance: accepting this ADR does not make any answer legally correct.

Invariants 1 to 5 and 7 apply: authorization precedes context construction (1), no citation without an authorized source in the same generation (4), every AI output has an insert-only `GenerationRecord` (5), and the gateway is the only egress chokepoint (ADR-006, ADR-026). Existing contracts this ADR builds on: `AuthorizeAction` and the proof (ADR-026), `PromptRenderer` with trust-bounded blocks (ADR-017), `TextEvidenceBuilder`/`GenerationRecorder` (ADR-016 and its amendment 2), `GenerateText` (ADR-006), audit in the mutating transaction (ADR-019). DAG: `grounded_generation` -> `access_control`, `ai_gateway`, `prompts`, `citations`, `documents` (verified against `module-dag.toml`; no `chunking` edge).

## Problem
Produce an answer from retrieved evidence such that: nothing unauthorized is ever read or sent; untrusted document text cannot take control of the generation; every statement of the answer points at real supplied evidence; every failure is explicit rather than an apparently grounded answer; and every generation is provable afterwards without storing content.

## Decision
**1. Flow (order is the security property; pinned by AST tests).** `GenerateGroundedAnswer.execute(ctx, command)`: (a) principal context only; command shape and `config_id` checked. (b) No claims: return `INSUFFICIENT_EVIDENCE` with no record; nothing authorized, read or sent. (c) Fresh decision for exactly `documents.read_document` over exactly the cited documents (strict: every document or none; one code `grounded_not_authorized`, no reason). (d) `TextEvidenceBuilder`: proof again, then, for each distinct cited version, **the lifecycle gate** (`ReadyVersionContent`: Documents' `ReadVersionState` must report the version `ready`, otherwise the single `citations_source_unavailable`; no text is touched first), then the chunk store, claim and passage-hash checks; the first chunk read happens only here. (e) Prompt rendering: trusted instructions; the question and each passage as separate untrusted blocks. (f) A **second** fresh decision immediately before egress; the gateway verifies it again before the provider call. (g) The reply is parsed against the answer contract; every quote is matched against the cited chunk text. (h) One transaction records the `GenerationRecord` and its audit fact. (i) For an `ANSWERED` outcome only, a third fresh decision over the cited documents; only if it succeeds are the statements (which carry chunk text as quotes) returned.

**2. Authorization is taken inside the use case**, not trusted from the caller or from the earlier search: a search result proves nothing about the caller's access now. Three decisions (before evidence, before egress, before release) shrink the revocation windows; the proof verifier's epoch check covers revocations during the read, and the gateway verifies the proof before every provider attempt, retries included. A revocation that lands after the last decision cannot be excluded: access is decided at a point in time, not held.

**3. Answer contract (JSON, strict).** **[OWNER: D1-D3 approved 2026-10-15]**
```json
{"outcome": "answered",
 "statements": [{"text": "The notice period is ninety days.",
                 "citation": "S1",
                 "quote": "shall give ninety days written notice"}]}
{"outcome": "insufficient_evidence", "statements": []}
```
Rules (all must hold; any violation rejects the whole reply, nothing is repaired): at most `max_output_characters`; strict JSON (no duplicate keys, NaN/Infinity, trailing data or code fence); exactly the keys `outcome` and `statements`; `answered` has 1..`max_statements`, `insufficient_evidence` has none; a statement has exactly `text`, `citation`, `quote` (strings); `text` is one printable line of at most `max_statement_characters`; `citation` is exactly one marker `S<n>`; `quote` is `min_quote_characters`..`max_quote_characters` characters; no control, format, surrogate, private-use, unassigned or line-separator character and no structural prompt marker in any text. Application checks: the marker names supplied evidence; the quote occurs, word for word and whitespace-insensitively, in the chunk text of exactly that marker (never in the rendered prompt, which contains delimiter lines). Defaults: 24000 / 20 / 1500 / 12 / 400.

**4. Outcomes and failure behavior.**
| Situation | Result | Record | Audit |
|---|---|---|---|
| valid answer | `ANSWERED` + statements | yes (citations = distinct cited, first-use order) | yes |
| model says `insufficient_evidence` | `INSUFFICIENT_EVIDENCE` | yes | yes |
| no claims | `INSUFFICIENT_EVIDENCE`, `record_id=None` | none (nothing generated) | none |
| contract violation, including an **empty or whitespace-only reply** (the provider answered, so a generation happened; this differs from "no claims") | `REJECTED` + stable `rejection` code, no statements | yes (`rejected`, no citations) | yes (`rejection` code) |
| not authorized (either decision, proof, read) | `AuthorizationError` | none | none |
| source unavailable / tenant mismatch / version not `ready` (`pending`, `failed`, `quarantined`) / document tombstoned / unknown | `NotFoundError(citations_source_unavailable)`, one code for all of them so the state cannot be probed; raised after authorization and before any chunk text is read | none | none |
| Documents' lifecycle service unavailable (the version's state cannot be read; an outage, not a state) | `InfrastructureError`, raised before any chunk text is read; not mapped to `citations_source_unavailable` so an outage is not reported as a missing source | none | none |
| Access Control unavailable at the release decision (answered outcome only) | `InfrastructureError`; statements withheld | yes (as for a revocation) | yes |
| grant revoked while the provider runs (answered outcome only) | `AuthorizationError(grounded_not_authorized)`; statements withheld | yes (the generation happened; only its release is refused) | yes |
| provider failure, timeout, rate limit | the gateway's error propagates unchanged | none (no output exists) | none |
| adapter raises something other than `ProviderFailure` (an adapter bug; the gateway translates only `ProviderFailure`) | the exception propagates unchanged; no answer | none | none |
| record or audit commit fails | `InfrastructureError`; the answer is withheld | none | none |
| no approved template configured | `ConfigurationError(grounded_template_unavailable)`, before any send | none | none |
Provider errors are never converted into answers; a timeout is not retried (ambiguous delivery, ADR-006).

**5. Trust boundaries (prompt-injection defense is structural, not wording).** (i) Only authorized, hash-verified chunk text enters; (ii) every passage and the question are untrusted blocks with the renderer's escaping of forged delimiters; (iii) the model has no tools and no side effects: its only effect is text; (iv) its reply is untrusted: strict parse, citation resolution against `EvidenceSet`, quote verification against stored text, character-class rejection; (v) a reply that obeys an injected instruction fails the contract (rejected, never shown); (vi) no text, quote, prompt or reply reaches logs, audit, records or errors; (vii) tenant isolation is inherited from authorization, the builder's tenant-bound reads and RLS on the record.

**6. Audit and record atomicity.** `@audited("grounded_generation.generation_recorded")`: the record insert is the effective mutation, so its audit fact commits in the same transaction (`SqlGroundedUnitOfWork`, which binds citations' transaction-bound repository through `bind_generation_records`). Attributes are labels only: `generation_outcome`, `citation_count`, `template`, `rejection`.

**7. Prompt template. [D8 owner-approved 2026-10-16]** `grounded_answer` v1 (`prompts/domain/catalog/proposed_grounded_answer.py`; the historical file name is kept so the path in the review request stays valid) is approved by the project owner for the exact instruction text with SHA-256 `2e3a3ce3b2b0a36bf212a4ed7ec3d07ec2f4ebee4f3882694071e48cd64cb94a` (1552 characters). It is `test_only=False` and the only entry of `PRODUCTION_TEMPLATES`. The production catalog serves exactly that `(template_id, version)`: any other selection fails closed with `prompt_template_unknown`, which this module reports as `grounded_template_unavailable` before any send. A wording change is a new version and needs a new explicit owner approval of the new hash; the approved hash is a literal in the pin tests, so a silent edit fails the build. The exact wording, its hash and the approval record are in `docs/ai/grounded-answer-v1-review-request.md`. The approval is not an approval by `ai-quality` or any team, and it does not make answers correct (see Limitations).

**8. Configuration (`grounded_generation` slice).** `model` is required (no default: a missing provider model fails closed at load); everything else has the defaults above plus `template_id=grounded_answer`, `template_version=1`, `max_output_tokens=1024`, `temperature=0.0`, `max_sources=20`. Bootstrap refuses `max_statements > citations.max_markers`.

## Rationale
Requiring a verbatim quote makes a fabricated source or quotation detectable by a deterministic check, which citation markers alone are not. One source per statement keeps every statement fully verifiable. Strictness over leniency (no repair, no fence stripping) removes parser-differential and smuggling surface. Authorizing inside the use case removes a class of caller mistakes. Rejection is a recorded, explicit outcome rather than a silent retry because a retry would send authorized text to a provider again.

## Alternatives considered
- Accept caller-supplied text: breaks provenance. Add a `chunking` edge: second text reader (ADR-016 amendment 2).
- Free-form answer with bracketed markers: cannot verify support; ambiguous parsing.
- Multiple citations per statement with one quote: only one of them would be verified.
- Partial grants (answer from the authorized subset): silently changes the answer and complicates the "all or nothing" proof; revisit if product needs it.
- Retry on rejected replies: new egress without new authorization semantics; deferred.

## Consequences
Models that wrap JSON in fences or paraphrase quotes will be rejected until the wording (or model) is tuned; that is the safe direction. Three authorization decisions per generation add two policy reads over the minimum. Two executions of the same request are two generations with two records (no idempotency key). Quote matching is whitespace-insensitive and case-sensitive.

**Limitations (explicit).** Unexpected provider exceptions are not translated here: the port contract requires adapters to raise only `ProviderFailure`, and no real adapter exists to verify that. `max_sources` is bounded here and by `citations`, but the gateway's `max_segments`, the renderer's `max_parts` and per-part size limits are separate settings; a mismatch fails closed (no send, no record, no release decision) where the smaller limit bites: a renderer `max_parts` below the number of sources fails before the pre-egress decision; a gateway `max_segments` below it fails after that decision and before the provider. Bootstrap cannot compare them (it receives built objects, not their limits), so this is behavior-tested, not start-up-checked. The release decision covers the *cited* documents only: a source that was supplied but not cited and is revoked during generation does not withhold an answer that quotes none of it. A revocation after the last decision cannot be ruled out; no continuous revocation guarantee is claimed. **Document lifecycle (finding of the Step 14 finalization review).** `ReadChunks` serves `pending` as well as `ready` versions, because chunking's own `index` stage reads a version before it can become `ready`. Retrieval only ever returns `ready` ones (ADR-015 section 4, invariant 11) and ADR-016 *assumes* callers cite only what retrieval returned, but nothing enforced that, and caller-supplied claims are references the use case only verifies against the stores. Before the fix a claim for a chunked, still-`pending` version (valid chunk id, ordinal and hash) sent that version's text to the provider and produced a recorded answer; reproduced on the unmodified code, then fixed. The fix, `ReadyVersionContent` (`grounded_generation/infrastructure`), is applied inside `build_grounded_generation` (a pin asserts it) and touches no frozen module, API-lock line, DAG edge or error code. `failed` and `quarantined` were already refused by `ReadChunks`; `pending` was the hole. **Not enforced, by owner decision (2026-10-15):** *currency*. An older `ready` version of a document is still eligible, because retrieval's current-version rule is a default search scope (ADR-008 section 5), not an access rule; a characterization test records this. Whether generation must also refuse superseded versions was an **owner decision** (it would need a rule for what "current" means); the owner decided on 2026-10-15 to keep the current behavior, so no currency rule is implemented. `ready` is monotone (no transition leaves it) and `ReadChunks` re-checks existence, so no new race arises between the gate and the read. This ADR text is a change to a *proposed* contract made during review; the owner approving D4/D5 approves it too, and should do so knowingly. `CODEOWNERS` has no entry for `src/lda/modules/grounded_generation/`; by project-owner governance decision of 2026-10-15 it stays unrouted (Owner decision record, "Ownership route"). A passing answer proves each cited source exists, was authorized and contains the quoted words. It does **not** prove the statement is entailed by the quote, and a malicious document can still supply a quotable misleading sentence. Entailment quality is evaluation's job (Step 17), not a runtime guarantee. No real provider adapter exists, so provider-side separation of instructions from context is unproven. The empty-claims path does not distinguish "no evidence found" from "no search was run".

## Security implications
Errors carry stable `grounded_*` codes only. The proof is a bearer credential handled as `Sensitive` and never returned. Content-derived hashes stay out of logs and responses. Authorization precedes context construction; unauthorized evidence is never read, built or sent (tests assert event order and provider-request contents).

## Migration implications
None: no schema, table or migration. The record table and its insert-only guarantees are unchanged.

## Operational implications
New slice `LDA_GROUNDED_GENERATION__MODEL` (required) and optional bounds. Nothing is deployed or scheduled. Retention of records remains undefined (ADR-016 amendment, item 6).
