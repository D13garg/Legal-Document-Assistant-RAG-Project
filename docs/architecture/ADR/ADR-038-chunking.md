# ADR-038: Chunking: eligibility, deterministic chunk sets, lifecycle lock and purge

## Status
Accepted

## Context
Step 8 follows ADR-010 §4 (stages after `scan`), ADR-037 (the extracted artifact, whose reader was left to this step) and ADR-023 (every downstream module purges its own derived data and keeps its own receipt). The frozen DAG already lists a `chunking` module with `depends_on = [document_processing, documents, ingestion]`, and `citations`/`retrieval` are planned to depend on it. The Step 8 brief says "implement chunking within `document_processing`, consuming extracted text through a clean public API". Those two statements only fit together if "within" means "within the document-processing pipeline": a stage that runs after `extract`. A module cannot consume its own text through a public API, and module-owned receipts and a module-owned schema (no cross-schema reads) require a module boundary. This ADR records that reading.

## Problem
Decide how chunking obtains extracted text without learning key layouts or re-implementing lifecycle rules; define a chunker that is deterministic, bounded and Unicode-safe; define the stored artifact, its identity and its immutability; make a re-run, a duplicate job, a crash and a concurrent purge safe; and decide what `DocumentDeleted` and `DocumentPurged` mean for derived chunks.

## Decision
1. **A new `chunking` module, reading through public APIs only.** `chunking` is its own module and schema (the DAG edge already exists). It never computes another module's key. `document_processing.api` gains `ReadExtraction(ctx: SystemContext, document, version) -> StoredExtraction` (`@public`, `@not_audited`), the only way another module obtains extracted text. It asks Documents first, then reads its own tenant-bound row, then reads the artifact and verifies its SHA-256 and recorded counts. `documents.api` gains `ReadVersionState(ctx: SystemContext, query) -> VersionStateView` (`@public`, `@not_audited`): identifiers and a status, no key, no bytes, no title. Both are additive and exported in the api locks.
2. **Eligibility.** Documents answers `not found` for a tombstoned or unknown document, a version of another document, and any other tenant's data (RLS). `ReadExtraction` accepts only `pending` (a stage is running) and `ready` versions; `failed` and `quarantined` raise `extraction_version_not_eligible`. A missing row, a missing object and a hash/count mismatch are distinct codes (`extraction_not_found`, `extraction_artifact_missing`, `extraction_artifact_corrupt`). The text is returned to a system caller only; serving it to a user or a prompt needs an `AuthorizedContext` (ADR-014) and is another module's decision.
3. **Deterministic chunker (pure domain, stdlib only).** Blocks are packed greedily in order up to `max_characters` (default 2000), never splitting a block that fits. A heading opens a new chunk once the current one holds `min_characters` (default 200), and a trailing heading moves to the next chunk with its content when both fit. A block longer than the ceiling is cut at a sentence end, else at whitespace, else at a code point that does not separate a combining mark, a joiner (ZWJ/ZWNJ) or a virama from what it binds; every cut lies after the middle of the window so progress is guaranteed; whitespace between pieces is the only text omitted. No overlap. Whitespace-only blocks are skipped; nothing to chunk is the permanent `no_chunkable_text`; more than `max_chunks` (default 50 000) is `limit_exceeded.chunks`, enforced while chunking. Offsets are code points. A chunk's text is exactly its segments' source text joined by `"\n\n"`, so any consumer can rebuild and verify it from the extraction. `chunker_version` is `chunk-1; max=…; min=…; unicode=<unicodedata version>`: a changed parameter or Unicode database never rewrites an existing set (§5).
4. **Artifact and identity.** One immutable object per version at `chunking/<doc>/<version>/chunks` (relative to the tenant prefix), written with `overwrite=False`: canonical JSON (sorted keys, ASCII, no whitespace) with `schema`, document/version ids, `extraction_hash`, `chunker_version` and the ordered chunks (`ordinal`, `id`, `text`, `text_hash`, `char_count`, `section_path`, `page_start`, `page_end`, `segments[[block, start, end]]`). `id` is a UUIDv5 over tenant, version, extraction hash, chunker version and ordinal: stable, never shared across tenants. `section_path` is the heading trail where the chunk begins (labels cut to 200 characters). Postgres holds identifiers, hashes, the chunker version and counts only, never text.
5. **Crash-safe idempotency, row first.** Per run: `ReadExtraction` -> chunk -> ONE fenced transaction (`fence.verify`, lifecycle lock, receipt check, insert-if-absent of the record) -> write the object -> confirm (§6). A row without its object is the only intermediate state; it is findable by purge, and a re-run completes it. A re-run over an existing record: same chunker version and same bytes `ADOPT`; a different chunker version `KEEP_RECORDED` (the recorded object is verified, never replaced); the same version with different output `CONFLICT` (`artifact_conflict`, permanent). A missing recorded object under another chunker version is `artifact_unrecoverable`.
6. **Lifecycle lock closes the late-write races.** `ChunkSetRepository.lock_document` takes a transaction-scoped Postgres advisory lock named by tenant and document. The stage holds it while it checks for a purge receipt and records (a receipt means nothing may be added), and again in a short read transaction after the object write; if a receipt exists by then, the stage deletes its own object and fails with `version_unavailable`. The purge takes the same lock in its final transaction, lists rows again, deletes and re-verifies the artifacts once more, then removes rows and writes the receipt. Consequence: a stage either records before the purge's final listing (the purge sees it and retries) or comes after the receipt (it refuses and removes anything it wrote). A failed cleanup is finished by the retry, which sweeps the object when it finds the document gone and a receipt present. This is stronger than ADR-037's accepted limitation for `extract`; the Step 7 behaviour is unchanged.
7. **Purge.** `PurgeChunks` is the handler of `DocumentPurged` (`chunking.purge_chunks`, `ASYNC_JOB`): list rows, delete artifacts, verify absence, then (under the lock) re-list, re-delete, re-verify, remove rows and insert an insert-only receipt (`scope = chunking.chunk_artifacts_and_rows`). Idempotent; a document with a receipt is left alone; a version set that changed in between raises a retried conflict. The receipt claims only this module's artifacts and rows, nothing about originals, extractions, embeddings, indexes or backups.
8. **`DocumentDeleted` needs no handler (decision, pinned by a test).** Chunking has no read path and its only consumer of extracted text is its own stage, which reads through `ReadExtraction` and therefore asks Documents first: from the moment of deletion nothing new is derived for the document and nothing is served. In-flight pipeline work is already cancelled by ingestion's own handler. A tombstone copied into this schema could only lag behind Documents' and would be a second source of truth. If a later step adds a read path here, it must check Documents on every read, and this decision must be revisited with it.
9. **No read path for chunk text yet.** `chunking.api` exports the stage, its parameters, the purge and its handler, and the failure codes. Retrieval (Step 11) decides how chunks are read, with its own ADR, `AuthorizedContext` where text can reach a prompt, and the lock/eligibility rules above.
10. **Persistence.** Schema `chunking`, migration `k0001` (branch `chunking`): `chunk_sets` and `purge_receipts`, forced RLS with tenant policies, tenant-leading keys, no cross-schema reference, no `UPDATE` grant plus a trigger rejecting updates for every role, `DELETE` only on chunk sets (purge), receipts insert-only with `TRUNCATE` blocked, CHECKs on hashes, chunker version and counts.
11. **Failure classification.** Permanent (`StagePermanentFailure`): `no_chunkable_text`, `limit_exceeded.chunks`, `version_unavailable` (document gone, version unknown or foreign, not eligible, or purged), `extraction_unavailable` (no row or object), `extraction_corrupt`, `artifact_conflict`, `artifact_unrecoverable`. Everything else (database, object store, a lost fence) propagates and is retried by the engine.
12. **Wiring and configuration.** `bootstrap/chunking.py` builds the stage and registers the purge handler; `bootstrap/documents.build_version_state_reader` and `bootstrap/processing.build_extraction_reader` build the readers before `build_ingestion`. The plan must be `[extract, chunk]` (a reversed plan fails closed with `extraction_unavailable`; tested). Slice `chunking` (ADR-031): `max_characters`, `min_characters`, `max_chunks`; an unsafe pair fails at composition.

## Rationale
Reading through `ReadExtraction` keeps key layouts private and makes the Documents lifecycle the single source of truth for eligibility. Making the pure chunker the only place where text is split keeps it testable by invariants (bounded, ordered, lossless, reproducible from segments). Recording the extraction hash and chunker version with every set gives answer provenance something exact to point at. The advisory lock is the smallest mechanism that turns "check receipt, then write" into an atomic decision across two modules' data without a cross-schema read.

## Alternatives considered
- Chunking code inside the `document_processing` package: contradicts the DAG, ADR-037's boundary and the receipt-per-module rule, and would have removed the public API the brief asks for.
- Using `GetDocument` for eligibility: it is `@requires`, a user-facing contract; calling it from system code would bypass what the marker declares.
- Mirroring a tombstone or status in `chunking`: a second source of truth that can lag.
- Overlapping chunks: duplicate text and ambiguous provenance; retrieval can add neighbours by ordinal.
- Storing chunk text in Postgres or a content cache: violates ADR-005/ADR-032.
- Full grapheme segmentation: no standard-library support; a dependency is not justified yet.
- A `DocumentDeleted` handler that deletes early: purge already follows deletion and a handler would race it.

## Consequences
One more module and schema, two additive APIs, one advisory lock per document, and about twice the text in the object store (extraction plus chunks). Memory per run is proportional to the extraction (bounded by ADR-037's `max_characters`). Known limits: hard cuts use combining-mark/joiner/virama rules, not UAX #29 (flag pairs, un-composed Hangul jamo and similar can be split inside an unbroken run longer than the ceiling); a sentence end is a heuristic (abbreviations such as "No. 5" are cut points only inside oversized blocks); a heading whose content does not fit with it stays alone; a different Python Unicode database changes the chunker version, not old sets. Object-store read-after-write consistency is assumed. A deleted document can still receive a chunk set from a run already in flight; the purge or the stage's own confirmation removes it.

## Security implications
Tenant comes only from the job row and the tenant-bound transactions; every statement carries the tenant predicate and RLS enforces it again; object keys are tenant-scoped; chunk ids never repeat across tenants. Text never reaches Postgres, events, audit, jobs, logs or reprs (tested end to end). `ReadExtraction` and `ReadVersionState` accept a `SystemContext` only and are reachable only from pipeline code. This step adds no scanner: the pipeline's mandatory `scan` stage is unchanged, no real content scanner exists, and ingestion is NOT production-ready.

## Operational implications
Configure the `events` queue (purge handler) next to `documents`, `ingestion` and `document_processing`; optionally the `chunking` slice. Dead-lettered `event:chunking.purge_chunks` jobs mean derived data of a purged document may remain: investigate, then replay. A persistent `version_unavailable` on a live document means Documents reports it as not eligible.

## Migration implications
`k0001` creates the schema (branch `chunking`). Add `CHUNKING_MIGRATIONS` to the migration locations. `documents.api.lock`, `document_processing.api.lock` and the new `chunking.api.lock` change additively; `.importlinter` is regenerated. Pins widened deliberately and listed in HANDOFF.md.
