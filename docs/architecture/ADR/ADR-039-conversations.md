# ADR-039: Conversations

## Status
Accepted

## Context
Approval state (2026-10-17): decisions **C1-C7 were approved by the sole project owner** in the Step 15 conversation, and the **project owner accepted Step 15 and this ADR on 2026-10-17**, based on the completed implementation, the validation report and the documented decisions. These are project-owner approvals only (a conversation record): no team approval is claimed and no code-owner review occurred (`CODEOWNERS` does not route the module, as in Step 14). Acceptance of the decisions does not remove the limitations listed under "Consequences" and "Security implications".

The approved DAG gives `conversations` exactly two dependencies, `citations` and `documents` (module-dag.toml, unchanged). Invariants 1 to 5, 7 and 12 apply: shared-schema multi-tenancy with forced RLS, no cross-schema reads or foreign keys, authorization before protected content, no content in logs/metrics/audit/exceptions/reprs, cross-module access through public `api/` only, no unvalidated answer text shown, and deletion that is provable. `GenerationRecord` is a content-free, insert-only provenance row owned by `citations` (ADR-016); ADR-016 amendment 2 and ADR-029 forbid persisting citation excerpts. `access_control` and `identity` are not dependencies of this module, and `@requires` is declaration-only today (ADR-014 section 11).

## Problem
Give users a durable conversation history that later steps (`answering`, Step 16) can append to, without (a) storing document-derived text, (b) re-implementing `citations` provenance or `documents` ownership, (c) adding an authorization dependency the DAG does not allow, (d) letting any message be edited, and (e) making deletion unbounded or unverifiable.

## Decision
**C1. Reference-only assistant turns [OWNER APPROVED 2026-10-17].** An assistant message stores the `GenerationRecord` identifier and nothing else: no answer text, no quoted excerpt. The record is content-free (ids, hashes, labels, citations), so **the answer cannot be reconstructed from it**; history shows that a turn happened and which record documents it, not what was said. This limitation is stated in the module README, in the `MessageView` docstring and by `MessageView.text_stored == False`. Persisting validated answer text needs a later ADR (it would store excerpts and require document-purge hooks).

**C2. Immutable, append-only messages [APPROVED].** Messages are never edited or individually deleted. Enforced twice: the domain builds only two shapes (`user`: client id + text; `assistant`: record id only), and PostgreSQL refuses every UPDATE and TRUNCATE (triggers, all roles), refuses any message DELETE unless its conversation is already gone (the `ON DELETE CASCADE` path, so deleting the conversation is the only way messages disappear), grants the runtime role only SELECT and INSERT on `messages`, and has CHECKs that make assistant text and mixed shapes impossible. Counter and sequence integrity are verified at commit by deferred constraint triggers.

**C3. No document or version references [APPROVED].** The module holds no document or version identifier. Provenance is represented only by the linked record id. A conversation may therefore span records that cite many versions; it does not pin a scope. The approved edge to `documents` is not declared because nothing imports it. The DAG is unchanged.

**C4. Owner-only authorization [APPROVED].** Every use case requires a `TenantContext` (a `SystemContext` is refused) and checks `conversation.owner == ctx.principal_id` together with the tenant; the repository never reads a conversation without naming its owner. Missing, other-tenant, not-owned and (after deletion) repeated-delete cases all raise `conversation_not_found` with identical code, message and detail. For assistant turns the record is read first through `citations.api` and must belong to the caller's tenant and principal, otherwise one code `conversation_record_unavailable`; because that check precedes any conversation lookup, the response never reveals whether a conversation exists. No sharing, grants or resource kinds exist; no `identity` or `access_control` dependency is added. **Live principal-status checks (disabled principals, session validity) are not performed in this module and must be enforced at the API/authentication boundary.**

**C5. One-transaction hard delete [APPROVED].** `DeleteConversation` deletes the conversation row (messages cascade), inserts an insert-only `DeletionReceipt` (tenant, conversation id, time, message count, scope `conversations.messages_and_rows`; no principal, no content) and one audit fact (identifiers and labels only) in one transaction; any failure rolls everything back. It verifies that the removed message count equals the counter and that nothing remains. It does **not** delete or mutate `citations` generation records, existing audit history or identity records, and it is **not** time-based retention and **not** comprehensive personal-data erasure (backups and other stores are out of scope). Deletion is bounded by enforced limits: at most 1,000 messages (database CHECK; configuration may only lower `max_messages`, default 200).

**C6. Idempotency in PostgreSQL [APPROVED].** A user message is keyed by `(tenant, conversation, client_message_id)`: same text returns the original (`replayed=True`, no write, no audit fact); different text is `conversation_message_conflict` without content. An assistant turn is keyed by `(tenant, record_id)`: same conversation replays, another conversation is `conversation_record_linked`. Appends lock the conversation row (`FOR UPDATE`) and advance a one-step counter; the unique constraints and the counter trigger are the backstop for races. `StartConversation` is not idempotent (each call creates a conversation).

**C7. Guards and governance [APPROVED; accepted with Step 15].** Two existing architecture tests were amended, both additively and neither weakened:
1. `tests/architecture/test_citations_boundaries.py`: the pin on who may import `citations` now admits `conversations` (its application code and `bootstrap/conversations.py`) through the public `citations.api` only, with the same strictness as for `grounded_generation` (production code in either consumer may import only `lda.modules.citations.api*`). This is the amendment C7 named.
2. `tests/architecture/test_audit_boundaries.py`: a consequence of C7 beyond the amendment named in it, disclosed in the Step 15 delivery report and now reviewed and accepted by the owner. ADR-019 D9 makes the audited-action map and the `@not_audited` exemption set exact, reviewed lists, so any new use case must be added to them. Added: four audited labels (`StartConversation` -> `conversations.conversation_started`, `AppendUserMessage` -> `conversations.user_message_added`, `AppendAssistantTurn` -> `conversations.assistant_turn_added`, `DeleteConversation` -> `conversations.conversation_deleted`) and two exemptions (`ReadConversation`, `ListConversations`, owner-only read queries; reads are not audited per ADR-019 D2). Nothing was removed or relaxed; the pins that every audited use case emits exactly one fact built from `ctx.tenant_id` and `attribution_of(ctx)` before commit, and that exempt use cases emit nothing, apply to the new classes unchanged. Necessity was demonstrated: the baseline version of this file run against the Step 15 tree fails `test_every_audited_use_case_emits_exactly_its_declared_action` and `test_the_not_audited_exemptions_are_exactly_the_reviewed_set` (2 failed, 14 passed); with the amendment all 16 pass.
`CODEOWNERS` is unchanged and does not route the module (as in Step 14). No code-owner review is claimed.

**Other settled conventions:** no title (additive later); use cases `StartConversation`, `AppendUserMessage`, `AppendAssistantTurn`, `DeleteConversation` (audited `conversations.conversation_started|user_message_added|assistant_turn_added|conversation_deleted`) and queries `ReadConversation`, `ListConversations` (`@not_audited`); audit attributes `sequence`, `record_id`, `generation_outcome`, `messages_deleted`; settings `LDA_CONVERSATIONS__MAX_MESSAGES|MAX_TEXT_CHARS|MAX_LIST` (hard ceilings 1,000 / 32,000 / 200 equal the database CHECKs); migration branch `conversations`, revision `n0001`, schema `conversations` with forced RLS on `app.tenant_id`.

## Rationale
Reference-only turns keep invariant 4 and ADR-016 intact and avoid a purge dependency on `documents`. Owner-only ownership is the only authorization this module can enforce without an edge the DAG forbids, and indistinguishable failures avoid an existence oracle. Database-level immutability and uniqueness make the guarantees independent of application bugs and of concurrent requests.

## Alternatives considered
Persisting answer text (rejected: stores excerpts, needs purge hooks and an ADR-016 amendment). Editable or per-message-deletable messages (rejected: edit history and audit complexity). A pinned document/version scope (rejected: needs the `documents` edge and eligibility rules; provenance already exists in records). Registering a resource kind with grants or adding `access_control`/`identity` (rejected: not in the DAG; enforcement is declaration-only). Two-phase tombstone plus purge job (rejected: no external objects; one bounded transaction is simpler and atomic). Deduplicating by content or request id (rejected: not deterministic across retries).

## Consequences
History cannot re-display an answer; Step 16 needs either regeneration or a separately approved decision. The API boundary must authenticate callers and refuse disabled principals. A deleted conversation frees its record to be linked again. `answering` (Step 16) is the only permitted future dependent.

## Security implications
Content never reaches logs, audit attributes, errors or reprs (`repr=False`, content-free codes, driver errors translated and unchained, commit-time failures translated). No cross-tenant reads, no FK out of the schema, forced RLS, column-level UPDATE grant, no TRUNCATE for any role. Residual: no live principal-status check; no claim of comprehensive erasure; embedded-PostgreSQL results are not CI service-container results; no load, provider or production-readiness claim is made.

## Operational implications
Config slice `conversations` (safe defaults). No jobs, events or object storage. One audit fact per effective mutation, in the same transaction.

## Migration implications
New independent branch `conversations` (`n0001`, `down_revision = None`), downgrade drops only schema `conversations`. No frozen-step migration changes. `api.lock` for the module is new (no removals elsewhere).
