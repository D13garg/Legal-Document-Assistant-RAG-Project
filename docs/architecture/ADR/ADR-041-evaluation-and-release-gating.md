# ADR-041: Evaluation persistence, typed configuration identity and fail-closed release eligibility

## Status
Accepted

## Context
Approval state (2026-10-18): decisions **D1-D5 were approved by the sole project owner** in the Step 17 conversation ("approve D1-D5 as recommended, subject to the safeguards below"). On **2026-10-18** the project owner also (1) approved the additive `chunking` and `citations` components of D1, (2) approved the D5 thresholds **as provisional deterministic regression and release-eligibility thresholds only**, and (3) **accepted Step 17 and this ADR**, based on the delivered implementation, the reported validation, the documented limitations and the verified archive (SHA-256 `5a5c3d39d4031bf2c5263c165a3d18ae08fd61bddf8d832d77c6c9d80738b72c`). This is a **project-owner approval recorded from a conversation**, not a team approval, code-owner review, CI approval, real-provider validation or production-readiness approval. Implementation and passing tests remain separate facts from acceptance, and acceptance removes none of the limitations listed below.

ADR-018 (accepted, Step 12) built a pure, offline evaluation core and explicitly deferred persistence, an activation state, binding activation to a passing report, CI wiring, production thresholds and judged metrics. ADR-030 defined `RagConfiguration` (free-form components, canonical JSON, SHA-256) and a fail-closed `decide` gate. Step 16 (ADR-040, accepted) records an operator-declared `config_id` on every generation: validated for the shape `rag-<64 hex>`, not computed. Nothing tied an evaluation, or a release decision, to the configuration that is actually running.

## Problem
A label that merely looks like a hash cannot authorize a release. Three gaps: (1) the identity components are free-form, so the same behaviour can hash differently and different behaviour can hash the same; (2) `answering` records whatever id the operator declares; (3) evaluation results are neither stored nor tied to the exact configuration, dataset and policy they were judged against, so a stale, edited or mismatched result could be mistaken for evidence.

## Decision
### D1. Typed, required configuration identity (owner-approved)
`evaluation.domain.effective_configuration.EffectiveConfiguration` has six required, validated components. Each field mirrors a real setting by name and bound (evaluation imports no other module):

| Component | Parameters |
|---|---|
| `prompt` | `template_id`, `version`, `content_sha256` (SHA-256 of the template instructions, UTF-8; the approved `grounded_answer` v1 hash is `2e3a3ce3...cb94a`, unchanged) |
| `generation` | `model`, `max_output_tokens`, `temperature`, `max_sources`, `max_output_characters`, `max_statements`, `max_statement_characters`, `min_quote_characters`, `max_quote_characters` |
| `retrieval` | `max_results`, `max_query_characters`, `candidate_pool`, `max_candidates` |
| `chunking` | `max_characters`, `min_characters`, `max_chunks` |
| `citations` | `max_sources`, `max_markers` |
| `answering` | `max_candidates`, `max_question_characters`, `max_sources` |

D1 named four components. `chunking` and `citations` were added after the explicit determination D1 requires for settings that affect evidence selection (chunk size decides what a passage is) and output validation (marker and source bounds decide whether an answer is accepted). **Owner clarification (2026-10-18): the project owner approved these two additive components because they affect evidence selection (chunk size decides what a passage is) and output validation (marker and source bounds decide whether an answer is accepted).**

Excluded, with reasons: credentials, URLs, paths and any deployment value (secrets and non-behavioural); `ai_gateway` timeout, retry, backoff and rate settings (operational); request-size ceilings of `ai_gateway` and `prompts`, which only refuse a request and never change a produced answer, and whose compatibility with included limits is checked at start-up; `retrieval.embedding_batch_size` (batching granularity); the evaluation harness's own limits; the declared `answering.config_id` (it is the output, not an input).

Canonicalization is the ADR-030 contract, unchanged (`evaluation.rag_configuration.v1`): components sorted by name, parameters sorted by name, `json.dumps(sort_keys=True, separators=(",", ":"), ensure_ascii=True)`, SHA-256 of the ASCII bytes, `rag-` prefix. There is one hashing implementation; `EffectiveConfiguration.configuration()` builds a `RagConfiguration`. Rules: no defaults inside the identity (the composition layer passes the effective, already-defaulted settings, so a default and the same value set explicitly hash identically while a changed default changes the identity); no absent/null values (every parameter is required); integers are exact Python `int` (booleans are refused); `temperature` is always a float and `-0.0` is normalized to `0.0`; strings match closed ASCII patterns, so no Unicode normalization question arises; sequences and maps are not used. A parameter added to a component enters the identity automatically (the component set and a hand-written golden canonical text are pinned by tests).

### D2. Runtime binding (owner-approved)
`bootstrap/rag_configuration.py` computes the identity from the real validated settings at the composition boundary and returns a `RuntimeConfiguration` whose id cannot be set independently. `LDA_ANSWERING__CONFIG_ID` becomes optional; if present it must equal the computed id or start-up fails (`rag_config_id_mismatch`). `build_answering` requires the `RuntimeConfiguration`, refuses one computed from different settings (`rag_runtime_configuration_mismatch`), and passes the computed id to `Answer`, which already forwards it to generation and the generation record. Compatibility: previously declared ids keep working only if they equal the computed id; generation records stored before Step 17 keep their old ids (insert-only) and match no evaluation. The three gate use cases accept only an `EffectiveConfiguration`, never a bare id.

### D3. Persistence (owner-approved, data-minimized)
Schema `evaluation`, migration `v0001` (branch `evaluation`), two **global, insert-only** tables with no tenant column and no RLS (synthetic data only; D3):
- `evaluation_runs`: identity `sequence`, `run_id`, `config_id`, dataset id/version/fingerprint, `evaluated_at` (epoch seconds), `passed`, `record_text` (canonical record), `record_sha256`. Database CHECKs: the hash equals `sha256(record_text)`; every searchable column equals the value inside the text.
- `release_eligibility`: identity `sequence`, `eligibility_id`, `run_id` (unique: one record per run), `config_id`, `dataset_fingerprint`, `run_sha256`, `run_passed` (must be true), `recorded_at`. A composite foreign key to the run's `(run_id, config_id, record_sha256, dataset_fingerprint, passed)` means a record can only describe an existing, passing run exactly.
Insert-only enforcement: no UPDATE/DELETE/TRUNCATE grant to the runtime role and row/statement triggers that reject change for every role including the owner; the application's immutability claim is backed by the database. Superseding is an INSERT of a newer row; history is never rewritten; there is no purge or retention path. Records hold identifiers, hashes, counts and scores: never a tenant, principal, document, question, answer or secret. Transactions: one per store call; reads use one REPEATABLE READ snapshot. Concurrency: concurrent runs all store (distinct sequences); an identical `run_id` stores once and the others get `evaluation_run_exists`; concurrent eligibility attempts for one run create one record and the rest replay it. There is no cross-module atomicity and none is needed.

### D4. Fail-closed eligibility (owner-approved)
`EvaluateConfiguration` runs the approved dataset and stores the run, pass or fail; a run that cannot be stored returns no result. `RecordEligibility` verifies, and only on success appends a record naming that exact run. `CheckEligibility` answers "eligible right now" and also requires an eligibility record for the newest run. A configuration is eligible only if the newest stored run on the approved dataset passes all of (pure `verify_run`, which trusts nothing stored):
1. hash of the stored text equals the stored hash and the text parses and is exactly canonical (else `eligibility_record_corrupt`; nothing else is trusted);
2. the configuration id recomputed from the stored components equals the effective id (`eligibility_config_mismatch`);
3. dataset id, version and fingerprint equal the approved dataset's (`eligibility_dataset_mismatch`);
4. the stored policy equals the approved policy (`eligibility_policy_mismatch`);
5. age is `0 <= now - evaluated_at <= max_age_seconds` in integer epoch seconds from the injected clock; the boundary second is valid, one more is `eligibility_evidence_stale`, a future timestamp is `eligibility_evidence_future`;
6. the run covers exactly the approved case ids in order and all thresholded metrics (`eligibility_incomplete`);
7. every metric mean, the error count and the gate decision recompute from the stored per-case scores and policy (`eligibility_inconsistent`);
8. the decision is a pass (`eligibility_run_failed`);
and no failing run for the same configuration and dataset exists within the age window (`eligibility_recent_failure`: a conservative rule so concurrent or flaky runs cannot hide a failure). Missing evidence is `eligibility_no_evidence`; no record is `eligibility_not_recorded`; a record naming an older run is `eligibility_superseded`. An infrastructure failure raises; `assert_release_eligible` converts it into a refusal. **An eligibility record means: eligibility was recorded for one specific verified configuration and its evidence at a point in time. It deploys nothing, changes no traffic and does not prove production readiness or legal correctness.**

### D5. Dataset, metrics and thresholds (owner-approved 2026-10-18 as PROVISIONAL deterministic regression and release-eligibility thresholds only)
`release-gate-synthetic` v1, code-defined in `evaluation/domain/release_dataset.py`, fingerprint `fb91a6010b43a0b7a3ba2e7a96ba53aa01c44546a29821d55f225901f53301f4` (pinned by a test). 14 fictional, legal-style cases: 5 single-source supported, 2 multi-source supported, 3 insufficient evidence, 3 isolation (sources the asker must never receive), 1 instruction-injection. Metrics are the five deterministic ADR-018 metrics over identifiers and outcomes. **Status of the thresholds: provisional. They are deterministic regression and release-eligibility criteria for this 14-case synthetic dataset. They are not validated production thresholds, they do not prove legal correctness, and meeting them does not establish production readiness.** Thresholds: `outcome_accuracy >= 0.95`, `retrieval_recall >= 0.90`, `citation_precision >= 0.95`, `citation_recall >= 0.90`, `isolation = 1.0`, all 14 cases required, error rate 0. Rationale: with 14 cases one miss moves a mean by about 7 points, so 0.95 on a whole-dataset metric means no miss, and 0.90 on per-case-averaged recall/precision tolerates at most the rounding of one partly-correct case; isolation is absolute because a leak is a security failure, not a quality dip; any errored case blocks because a crash is never a good result. Maximum evidence age: `evaluation.max_evidence_age_seconds`, default 604,800 (7 days), bounded 60..2,592,000. Expected failure behaviour: a miss produces a stored, failing run and no eligibility. **Judged (LLM) metrics remain deferred** (ADR-018 section 6).

## Rationale
Computing the id from the typed components, at the one boundary that sees every module's settings, removes the possibility of a label drifting from behaviour. Storing the canonical record text with a database-checked hash, and re-verifying everything on read, means tampering must defeat both the database constraints and an independent recomputation. Global tables are acceptable only because the data is synthetic and content-free; the schema says so and the tests assert it.

## Alternatives considered
- Keep free-form components or a declared id: rejected, it is the gap this ADR closes.
- Hash an environment dump or object repr: rejected (secrets, ordering, representation drift).
- Tenant-scoped, RLS-protected tables: rejected, there is no tenant and forcing a fake one would be misleading.
- Pass/fail report only, no persistence (D3 option B): rejected, cannot bind evidence to a configuration over time.
- Trust the newest passing run only: rejected, concurrent runs could hide a failure; replaced by the recent-failure rule.
- Add `ai_gateway`/`prompts` edges to `evaluation`: not needed; the template hash is read by the composition layer, so the DAG is unchanged.

## Consequences
`answering` settings: `config_id` optional; `build_answering` has a new required `runtime` argument (existing callers and three existing tests were updated, not weakened). `evaluation` gains an infrastructure layer, a schema and a migration; its Step 12 "pure, schema-less" architecture pins were amended so the pure core (domain, application, api) stays pure and persistence is confined to `infrastructure/persistence`. `evaluation/api.lock` gained 166 lines and lost none. The DAG, `CODEOWNERS`, the approved prompt template and its hash are unchanged. `.importlinter` was regenerated for the new layer. Changing any setting in the identity invalidates prior evaluations by construction.

## Security implications
No tenant data, question, answer, passage or secret is stored or logged; errors are stable codes; database failures are translated and chained away. Authorization: not applicable to global synthetic evaluation, and nothing here constructs or handles an authorization proof; the evaluation target is expected to run the real authorization path as a dedicated evaluation principal (ADR-018). The runtime role is the one that can write evaluation tables (ordinary schema grants); there is no separate evaluation-writer role, so any code holding the runtime database credentials can append runs or eligibility records. The verifier detects a forged failing-to-passing edit, but a writer who runs the real evaluation honestly against a fake target is not detectable by this design. **The eligibility record is evidence for a human or pipeline decision; it is not an access control.**

## Operational implications
Rolling out requires `LDA_ANSWERING__CONFIG_ID`, if set, to equal the computed id (the computed value is the supported way to obtain it). Eligibility expires after the maximum age and must be renewed by re-running evaluation and recording. Nothing blocks a deployment automatically: wiring `assert_release_eligible` into a start-up or pipeline step is a later decision.

## Migration implications
Migration `v0001` creates schema `evaluation`; downgrade drops it with CASCADE (destroying evidence) and is tested. Existing generation records keep their old declared ids.

## Testing and verification evidence
See the Step 17 section of `HANDOFF.md` for exact commands and results. Coverage: golden identity written by hand from the contract, per-parameter sensitivity, exclusions, validation, runtime binding and start-up refusal, verifier tamper cases (including a recomputed-hash edit), age boundaries, every fail-closed code, in-memory and real-PostgreSQL stores, database-enforced integrity and insert-only behaviour, the eligibility foreign key, idempotency, concurrency and migration up/down, plus architecture pins. Evidence is from embedded PostgreSQL (`pgserver`), not a CI service container.

## Known limitations
- The metrics see identifiers and outcomes, not answer text: no entailment, legal correctness, completeness or fluency measure. 14 cases is a coarse regression set, not a benchmark.
- The only targets in this step are deterministic test doubles. **No real provider, real embedder, real scanner, CI, load, fuzz, penetration or production-readiness evidence exists.** A production `EvaluationTarget` that drives the real pipeline as a dedicated evaluation principal is not built here.
- Embedding model identity and chunker version are not in the identity: no setting for them exists yet.
- Invalid-output handling is covered by the `grounded_generation` failure matrix, not by these metrics.
- No separate evaluation-writer role; no retention or purge path; no automated release workflow.
- Step 16 limitations (answer text not stored, no exactly-once generation, retention/erasure unresolved, HTTP layer absent) are unchanged.

## Deferred concerns
Judged metrics; production target adapter; CI wiring; embedder/chunker version identity; evaluation-writer role; retention; automatic release enforcement (Step 18 or later).

## Amendment (Step 18 follow-up: duplicate-write handling in the evaluation store)
Authorized by the sole project owner (conversation record, 2026-10-19; not a team approval or code-owner review) as a narrowly scoped defect correction after ADR-042 was accepted.

**Root cause (reproduced and attributed with SQLSTATE and constraint name only; no parameters or row values captured).** `SqlEvaluationStore.append_run` and `record_eligibility` named one column as the `ON CONFLICT` arbiter (`run_id`). A named arbiter covers only that index, so a concurrent duplicate could trip a *different* unique constraint first and raise PostgreSQL `23505` (`UniqueViolation`), which `_run` translated to `PERSISTENCE_FAILED` instead of the documented outcome. Observed constraints: `evaluation_runs_run_id_config_id_record_sha256_dataset_fing_key` (the composite `UNIQUE (run_id, config_id, record_sha256, dataset_fingerprint, passed)` that the eligibility foreign key needs) for runs, and `release_eligibility_eligibility_id_key` for eligibility. The defect pre-dates Step 18 (reproduced on the untouched Step 17 archive).

**Correction (2 lines, `src/lda/modules/evaluation/infrastructure/persistence/store.py`).** Both inserts now use `.on_conflict_do_nothing()` with no arbiter. *Runs:* every unique constraint on `evaluation_runs` contains `run_id` (the identity `sequence` primary key cannot collide), so every suppressed conflict means that `run_id` already exists, which is exactly `RUN_EXISTS`. *Eligibility:* a skipped insert is resolved by a read-back. **The first version of this read-back keyed only on `run_id` and was incomplete: it is superseded by the follow-up correction at the end of this amendment.** `ON CONFLICT` suppresses only unique and exclusion violations: CHECK, foreign-key, type and connection errors still propagate. No schema, constraint, migration, grant, RLS policy, trigger, API lock, DAG edge or public signature changed, and no `IntegrityError` is caught or translated by application code.

**Eligibility path: independently tested, confirmed vulnerable, and fixed.** The existing eligibility concurrency test gives every thread a distinct `eligibility_id`, so it could only ever collide on `run_id` and could not expose this. The production use case (`release_gating.py`) generates a fresh UUID per call, so the race needs a caller that retries concurrently with the *same* `eligibility_id` through the store port. Measured on the unfixed code with synchronized threads: 5 contract-violating rounds in about 4,200 (about 0.1%), each an `IntegrityError` `23505` on `release_eligibility_eligibility_id_key`. It is rare and not reachable through the production use case, but the port contract makes a same-id retry a replay.

**Contract impact.** Under concurrent duplicates a loser now always gets `ConflictError(RUN_EXISTS)` (previously occasionally `InfrastructureError`), and concurrent same-id eligibility retries all succeed as one record plus replays (previously occasionally `InfrastructureError`). Single-threaded behavior is unchanged. Reusing an `eligibility_id` for a different run failed as `PERSISTENCE_FAILED` only when that run had no record of its own; when it already had one, the first version returned that record as a replay. That was wrong and is fixed in the follow-up correction below.

**Evidence (local only: embedded PostgreSQL via `pgserver`, Python 3.12.3; CI not run; `adr-gate` not run; no mutation-testing tool run).**
- Unfixed code, the original failing test alone: 4 of 80 runs failed here (an earlier session also saw 5 of 40 on both the Step 18 tree and the pristine Step 17 archive). Barrier-synchronized probes, 12 threads: runs 21 of 1,200 rounds violated the contract (about 1.8%); eligibility with a shared id 5 of about 4,200 rounds.
- New tests, `src/lda/modules/evaluation/tests/integration/test_conflict_handling.py` (7 tests): a deterministic statement-shape test (executed SQL contains `ON CONFLICT DO NOTHING` and never `ON CONFLICT (`); a same-run-id/different-content conflict that changes nothing; an unrelated database error (`bigint` overflow) that is neither suppressed nor reported as a conflict; a same-id sequential eligibility replay; a cross-run `eligibility_id` reuse that fails and keeps the original; and two barrier-synchronized statistical tests (200 rounds of 12 duplicate runs; 1,000 rounds of 12 same-id eligibility retries).
- Against the **original** `store.py` (scratch copy): the shape test failed 3 of 3, the run barrier test 3 of 3, the eligibility barrier test 2 of 3; the four contract tests pass both before and after, as intended.
- Fixed code: the originally failing test passed 100 of 100; the new file passed on every execution (5 dedicated repeats plus the module and full-suite runs); the evaluation module suite passed (182 = 175 + 7); `make check` exit 0, **3,841 passed** (3,834 + 7), 1 warning. `tests/.../test_release_persistence.py` is byte-identical to Step 17 (no existing test changed, skipped or weakened).

**Residual uncertainty.** The barrier tests are statistical: the race cannot be forced from SQL, a pass is strong evidence and not a proof, and the eligibility race is rare enough that a single pre-fix execution detects it only about two times in three. The deterministic shape test is the reliable guard. Other store paths were not exhaustively race-tested. This is persistence-concurrency evidence only; it says nothing about application startup, production readiness or any deployed system.

### Follow-up correction: an eligibility_id that belongs to a different run
Authorized by the sole project owner (conversation record, 2026-10-19; not a team approval or code-owner review) as a narrow defect correction. ADR-042 stays **Accepted**; D1-D5 and the startup-validation exception are unchanged. This corrects a defect in the first version of the eligibility fix above; it does not revert it.

**Edge case.** Run A has eligibility record E-A and run B has its own record E-B. A call to record E-A for run B skips its insert (E-A already exists for another run). The first version then read back by `run_id` alone, found E-B, and returned it as a successful replay, so the conflicting call reported success instead of failing. The first fix's test covered only a run B with no record of its own.

**Correction (`src/lda/modules/evaluation/infrastructure/persistence/store.py`, `record_eligibility` read-back only).** The insert, with its unqualified `ON CONFLICT DO NOTHING`, is unchanged. The read-back is now one statement that returns every row whose `eligibility_id` is the supplied id or whose `run_id` is the requested run (one snapshot, no read-then-write sequence), resolved as follows:
- the supplied id exists and belongs to the requested run: that record (a replay unless this call inserted it);
- the supplied id exists and belongs to a different run: `PERSISTENCE_FAILED`, even when the requested run has its own record;
- the supplied id does not exist and the requested run has a record: that record, as a replay (concurrent calls with different generated ids still converge to one record);
- neither: `PERSISTENCE_FAILED`, as before.

*Visibility:* a skipped insert means the conflicting row is already committed (`ON CONFLICT` waits for an in-progress writer to finish), so a `READ COMMITTED` read in the same transaction sees it. No schema, constraint, migration, grant, RLS policy, trigger, API lock or DAG change; `index_elements` does not reappear.

**Evidence (local only: embedded PostgreSQL via `pgserver`, Python 3.12.3; CI not run; `adr-gate` not run).** Three tests added to `test_conflict_handling.py` (now 10): the exact sequence A, B, E-A, E-B, then E-A offered for B (must fail with `PERSISTENCE_FAILED`, two records remain, E-A still A's and E-B still B's, B's own replay still works); 12 synchronized callers offering E-A for B (all must fail); and 150 rounds where half the callers offer E-A for B while half offer their own fresh ids (reuse never succeeds; fresh ids converge to one record plus replays). Against the previous checkpoint's `store.py` the three new tests failed on every one of 3 trials and the other 7 passed, so the edge case is deterministic. On the fixed code the module passed on 5 executions, the originally failing run-race test passed 60 of 60, the evaluation module passed (185 = 182 + 3), and `make check` exit 0 with **3,844 passed** (3,841 + 3).

**Residual noted at the time (since fixed by the second follow-up below).** If the supplied `StoredRun` carried a wrong hash but the run already had a record, the call returned that record as a replay without writing. The barrier tests are statistical evidence, not proof; the deterministic tests are the reliable guards.

### Second follow-up: run identity (the record hash) is checked on replay
Authorized by the sole project owner (conversation record, 2026-10-19; not a team approval or code-owner review) as a narrow defect correction. ADR-042 stays **Accepted**; D1-D5, the duplicate-run fix and the eligibility-id collision fix are unchanged.

**Defect (reproduced, deterministic).** If a run already had an eligibility record, a request carrying that `run_id` but a different `record_sha256` was returned the existing record as a successful replay. The insert already refuses such a request (its `WHERE` requires the stored run's hash to match; its docstring says "a hash that differs inserts nothing and fails"), but the read-back checked only `run_id`.

**Identity contract (from the repository, nothing invented).** A stored run is identified by `(run_id, record_sha256)`: the schema binds an eligibility record to both through the composite foreign key `(run_id, config_id, run_sha256, dataset_fingerprint, run_passed)` referencing the run's `(run_id, config_id, record_sha256, dataset_fingerprint, passed)`. `config_id`, `dataset_fingerprint` and `passed` are copied from the stored run row by the insert, never taken from the caller, and the foreign key enforces them. Of the four `StoredRun` fields, `record_eligibility` consults only `run_id` and `record_sha256`. `record_text` is determined by `record_sha256` (database CHECK `record_sha256 = sha256(record_text)`) and `sequence` is a surrogate key; neither is read. A probe in a scratch copy confirmed that a tampered `record_text` or `sequence` behaves identically to a genuine one on both the fresh-insert and the replay path, so they are not identity-bearing and were left alone. `record_sha256` is therefore the only identity field that can mismatch while `run_id` matches.

**Correction (`store.py`, read-back only).** A new helper `_is_this_run` requires the stored eligibility record's `run_sha256` to equal the supplied `record_sha256` before any record is returned, on both the by-id and the by-run resolution paths; otherwise `PERSISTENCE_FAILED`, the existing contract. The insert, both unqualified `ON CONFLICT DO NOTHING` clauses and the id-ownership rule are unchanged. No schema, constraint, migration, grant, RLS policy, trigger, API lock or DAG change; no error is caught or translated more broadly.

**Evidence (local only: embedded PostgreSQL via `pgserver`, Python 3.12.3; CI not run; `adr-gate` not run).** Five tests added to `test_conflict_handling.py` (now 15): a deterministic test over two wrong-hash kinds (all zeros; another run's real hash) times two id kinds (the existing record's id; a fresh id) asserting `PERSISTENCE_FAILED`, that the run and eligibility tables are byte-for-byte unchanged, and that the true run still replays; and a synchronized test (100 rounds) where wrong-hash callers race right-hash callers for one run (wrong always fail, right always converge to one record). Against the pre-fix code all 5 failed (`DID NOT RAISE`); the 10 earlier tests in the module are unchanged and pass. On the fixed code the module passed on 5 executions, the original run-race test passed 60 of 60, the evaluation module passed (190 = 185 + 5), and `make check` exited 0 with **3,849 passed** (3,834 + 15).

**Residual.** Supplied `record_text` and `sequence` are ignored by `record_eligibility` (verified, unchanged, not identity-bearing). The barrier test is statistical evidence; the deterministic tests are the reliable guards. Persistence evidence only: not production readiness, and not application startup.
